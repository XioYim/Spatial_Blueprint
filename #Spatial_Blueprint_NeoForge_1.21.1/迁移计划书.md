# Spatial_Blueprint → NeoForge 1.21.1 迁移计划书（梗概）

> 写于：2026-09-29（主会话，Healthy_Diets 的 1.21.1 迁移做到 P4 时顺带起草）
> 定位：**只写梗概、思路与经验**。逐文件分析、API 对照表、决策点的方案比较留给后续专门的对话。
> 参照样板：Healthy_Diets 的 1.21.1 迁移（`D:\Mods\Healthy_Diets_NeoForge_1.21.1\#Healthy_Diets_NeoForge_1.21.1\迁移计划书.md`、那边的记忆 T1–T6 / K1–K7 / C1，开发日志 e01–e11）。

## 一、梗概

- **源头**：`D:\Mods\Spatial_Blueprint`，Forge 1.20.1（47.4.10），`mod_version=2.8.2`，modid `spatial_blueprint`，包根 `com.xioyim.spatialblueprint`。
- **目标**：新建姊妹项目（建议 `D:\Mods\Spatial_Blueprint_NeoForge_1.21.1`），NeoForge 21.1.x + Java 21 + ModDevGradle，两条线并行维护。版本号建议从 3.0.0 起，和 1.20.1 线的 2.x 分开。
- **规模**（2026-09-29 粗扫）：220 个 java 文件，约 5.08 万行，大约是 Healthy_Diets 的两倍。
  - network 79 个、gui 44 个、util 35 个、client 30 个、item 13 个，其余零散。
  - 最大的文件：BlueprintSelectionRenderer 2520 行、PlacementScreen 1982 行、BlueprintLibraryScreen 1590 行、BlueprintSanitizer 1317 行、BlueprintPlacementHandler 1311 行。
- **比 HD 省事的地方**：没有 mixin，没有 capability，只有 2 处 ForgeRegistries，唯一外部依赖是 JEI（compileOnly）。Create 胶水只通过实体 NBT 处理，不依赖 Create 本体。
- **比 HD 难的地方**：物品 NBT、蓝图文件格式、选区渲染、配置系统、客户端 / 服务端分边，见第三节。

## 二、总体思路（沿用 HD 已验证的做法）

1. **新项目、不原地改**：1.20.1 线继续可发版，新线放在同一 GitHub 仓库的 `neoforge-1.21.1` 分支（2026-09-29 用户拍板，取代「独立 git」；本机克隆在 `D:\Mods\Spatial_Blueprint_NeoForge_1.21.1`，两条线只 cherry-pick、不整体合并），交接件结构照抄 HD 1.21.1 项目的布局（项目记忆 / 待办 / 开发日志 / 测试清单 / 功能联动手册）。
2. **两条线共用一份「功能联动手册」**：子系统 → 两边文件 → 1.20.1 记忆编号 → 1.21.1 状态；修 bug / 加功能当场登记另一边要不要跟（HD 的 T2）。
3. **按层分阶段，一个阶段一个 TASK，辅助 AI 执行、主会话验收后才派下一个**。建议分期（具体边界留给后续对话）：

| 阶段 | 内容 | 备注 |
|---|---|---|
| P0 | MDK 骨架 + 交接件 + 本计划书细化 + 决策点拍板 | 主会话自己做 |
| P1 | 纯逻辑层：配置数据类、蓝图数据模型、变换 / 预算 / 净化等 util | 不碰 MC 注册与网络 |
| P2 | 注册与数据：物品、方块 / 方块实体、**物品数据组件**（取代物品 NBT）、SavedData | 决策点 D1、D2 在这之前定 |
| P3 | 网络：79 个消息改 `CustomPacketPayload` + `StreamCodec`，一个注册器 | 协议版本规则要重定（D4） |
| P4 | 服务端逻辑与命令：捕获、放置、净化、上传检测、权限归属 | 最大风险是蓝图文件兼容（D2） |
| P5 | 客户端基础：选区渲染、outliner、HUD、按键 | 渲染 API 改动集中在这里 |
| P6 | 界面：44 个 gui（按引用簇拆 2～3 个任务） | 每个任务都要 runClient 手测 |
| P7 | 联动：JEI | 量很小 |
| P8 | 1.21.1 测试环境、部署、全量回归 | HD 已建好 1.21.1 专服与客户端，可共用 |

4. **主会话在辅助 AI 执行期间做下一阶段的取证附件**（HD 的 NF-003 / 004b / 005 / 006 附件做法）：逐文件清单、javap 结论、要打的桩。派任务时附件必读，辅助 AI 不用自己推导。
5. **迁移桩**：本阶段不迁的依赖一律「注释掉那一条调用 + 上一行 `// SB-TODO(P<阶段>): <类名>`」，每阶段报告里写「新桩条数 + 存量 = grep 实数」，后续阶段逐步清零。

## 三、本项目特有的难点（只点名，分析留给后续对话）

1. **物品 NBT → 数据组件**：168 处 / 25 个文件读写物品 NBT（13 个蓝图物品类、各 C2S 消息、若干界面）。1.21 物品没有 NBT，要为蓝图物品设计自定义组件（record + Codec + StreamCodec）；组件取出来是副本，改完必须写回（HD 最大的坑，见第四节）。
2. **蓝图文件与旧数据兼容**：蓝图以 NBT 文件存盘（`NbtIo.readCompressed` 18 处、SavedData 20 处），里面有方块状态、**方块实体 NBT、实体 NBT、容器里的物品**。1.20.5 起物品存储格式整体改了（`tag` → `components`），方块实体也改走 `saveWithFullMetadata(Provider)` / `loadWithComponents(tag, Provider)`（已 javap）。1.20.1 线捕获的蓝图、以及导入的 litematic / schem / schematic，要走原版 DataFixer 按 DataVersion 升级，否则箱子里的东西会丢或读错。目前代码里只有 1 处涉及 DataVersion。→ 决策点 D2。
3. **选区 / 预览渲染**：BlueprintSelectionRenderer（2520 行）与 client/outliner 系。1.21 的顶点 API 从 `vertex().color().endVertex()` 链式调用改成 `addVertex(...)` / `setColor(...)`（已 javap），BufferBuilder、RenderType、RenderLevelStageEvent 的阶段也要重新核对。编译能过不代表画得对，必须 runClient 看。
4. **配置系统**：ForgeConfigSpec 125 处 / 12 个文件 → NeoForge `ModConfigSpec`（已确认存在）。T8 里 `ConfigAccess` 服务端镜像、`SPEC.getSpec().get(path)` 查 ValueSpec 这类细节要逐条复核。
5. **客户端 / 服务端边界**：`DistExecutor` / `@OnlyIn` 分布在 88 个文件。NeoForge 1.21 不再按 `@OnlyIn` 剥离代码，客户端逻辑要挪到嵌套类或 `@Mod(dist = CLIENT)` 入口（HD P3 的做法）。
6. **网络**：79 个消息，还有「蓝图分片推送」（`sendBlueprintTo` + `CHUNK_SIZE` + `MAX_TOTAL_CHUNKS`，T10）。NeoForge 自带大包拆分（HD 已取证：两个方向的大包都由 `GenericPacketSplitter` 自动拆），可以评估自有分片还要不要保留（保留最稳，行为不变）。
7. **协议版本 = mod 版本**（T3）：1.21.1 的 `registrar.versioned(...)` 可以继续用 mod 版本，也可以像 HD 一样另立 PTC。→ 决策点 D4。
8. **界面**：44 个 gui，GuiGraphics 用量大（658 处 / 73 个文件）。1.21 的 `Screen.render` 自己先画模糊背景，老写法会把自绘面板盖住；`mouseScrolled` 多了一个参数（HD 的 NF-006 附件第三节有完整清单，直接复用）。

## 四、从 Healthy_Diets 迁移带过来的经验（直接照做）

**构建与取证**
- Java 21（Zulu 21），和 1.20.1 线的 Java 17 各设各的 `JAVA_HOME`；不要在一个项目目录里跑另一个项目的 gradle。
- javap 取证看 `build\moddev\artifacts\neoforge-<版本>-merged.jar`（vanilla + NeoForge、官方映射）；FML 注解类在 gradle 缓存的 fancymodloader loader jar 里。
- `neoforge.mods.toml` 模板经 `${}` 展开，**注释里不能写反斜杠和 `$`**（HD 的 K4，P0 就踩过）。
- 验编译 `compileJava --rerun`，警告基线在 P0 实测后重立（HD 是 0）。

**验收方法**
- **mtime 窗口会漏掉「复制来的文件」**（Windows 复制保留源 mtime）。迁移类任务验收一律「目标项目全量文件列表 vs TASK 允许清单」`comm` 比对，再逐个和源文件 `diff -w --strip-trailing-cr`，滤掉 import / 注解 / 样板之后看残差（HD 的 K5）。
- 每个阶段都要求辅助 AI 写 GameTest；GameTest 要用真实结构文件，`@GameTest(template = "empty")` + `@PrefixGameTestTemplate(false)`；mock 玩家接口已删，需要 ServerPlayer 用 `FakePlayerFactory`（HD 的 K6）。
- 往返字节测试的样本容器要和 decode 同型（HD 的 K7）。
- 用 FakePlayer + `NeoForge.EVENT_BUS.post(事件)` 做「事件处理器真的挂上了」的接线测试，比只测序列化有用得多（HD 的 NF-004a）。
- 测试会往开发目录 `run\` 写配置残留，会挡住默认配置生成。测试结束要自己清理，或者用单独的 gametest 目录。
- runServer 验收要正常 stop，不要强杀进程树。

**1.21 API 的坑（HD 已踩、已取证）**
- **组件取出是副本**：凡「取出来改字段」都要写回，漏了不报错，只表现为数据不变 / 合并不落盘。HD 用脚本审计「读了、改了、没写回」和「中间自写回后又用旧数据覆盖」两类（开发日志 e10），SB 的蓝图物品组件照做。
- 堆叠判定 = 物品 + 组件完全相等（`isSameItemSameComponents`），组件里不要放会变的时间戳之类。
- 事件 API：拾取事件 Pre 不可取消、改 `setCanPickup(TriState.FALSE)`；`TickEvent` 改 `PlayerTickEvent.Post` 等；`MobEffectEvent.Applicable` 结果改枚举；`RightClickBlock.getUseBlock()` 返回 TriState；`@EventBusSubscriber` 在 `net.neoforged.fml.common`，mod 总线那种写法已废弃（会多出警告）。
- 网络：handler 默认在主线程，去掉 `enqueueWork` / `setPacketHandled`；`FriendlyByteBuf.writeComponent` 已删，Component 走 `ComponentSerialization.TRUSTED_STREAM_CODEC`；`Component.Serializer` 必须带 `HolderLookup.Provider`，不要用 `RegistryAccess.EMPTY`。
- SavedData：`save / load` 多一个 `HolderLookup.Provider` 参数，`computeIfAbsent` 吃 `SavedData.Factory`。
- 注册表查缺键返回默认值（空气）不是 null，判存在用 `containsKey`。
- `ItemStack.of(tag)` 已删，改 `ItemStack.parse(provider, tag)`，返回 Optional。

**协作**
- TASK 手册第一段备份、第二段只给项目记忆路径；报告禁止代码块、只给「主张 + file:line」。
- 主会话写任务书时，**把能 javap 的都先 javap 了写进「已定方案」**，辅助 AI 只管照做；有异议写进报告，不自己改方案。
- 任务书也会写错（HD 的 NF-003 把一条校验方向写反了，辅助 AI 按源码纠正）。任务书里写「以源码为准」，并要求有出入时在报告里指出。
- 派任务前工作区必须干净：主会话先提交文档再派；执行期间主会话不提交、不写开发日志。
