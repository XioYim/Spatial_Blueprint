三、已定方案
========================================================

总原则同 SBN-005～010：字段、校验、上限常量、翻译键、日志文本、判断顺序一律不改；按 BlueprintNetwork 类注释（C14）改写。
每个文件 diff -w 残差逐条进报告。

1. BlueprintNetwork：register 里追加 PlaceBlueprintMessage 一条，playToServer（1.20.1 是 c2s）。payload ID place_blueprint_message。其余零改动。

2. BlueprintPlacementHandler 改写点
   a. 事件：@Mod.EventBusSubscriber → @EventBusSubscriber(modid = SpatialBlueprintMod.MODID)（游戏总线）；
      TickEvent.ServerTickEvent + phase END → ServerTickEvent.Post（去掉 phase 判断）；
      ServerStoppingEvent / PlayerEvent.PlayerLoggedInEvent / PlayerLoggedOutEvent / BreakSpeed / LevelEvent.Unload 换 net.neoforged.neoforge.event 同名类。
   b. 领地：BlockSnapshot.create(dim, level, pos) 与 BlockEvent.EntityPlaceEvent(snapshot, placedAgainst, entity) 换 neoforge 包，
      MinecraftForge.EVENT_BUS.post → NeoForge.EVENT_BUS.post，取消判定用 isCanceled()（C23 同口径）；BreakEvent 同 SBN-010。
   c. 方块实体：be.load(nbt) → be.loadWithComponents(nbt, level.registryAccess())（全部 8 处，含 restoreUndo）；
      saveWithFullMetadata() → saveWithFullMetadata(level.registryAccess())（snapshotRegion）。
   d. MobEffects.GLOWING 在 1.21 是 Holder，new MobEffectInstance(Holder, int, int, boolean, boolean) 构造直接可用（J45）。
   e. 网络：CHANNEL.send(PLAYER…) → BlueprintNetwork.sendToPlayer（sendPlacementFailure 2 处、onPlayerLogin 1 处、sendPlacementProgress 1 处）。
   f. EntityType.create(CompoundTag, Level)、setChunkForced、BlockState.rotate(Rotation)、playSound 在 1.21 签名不变（J45），原样。
   g. pendingPlacements / pendingGlowTasks 仍是 static 表，只在服务端主线程读写（onServerTick、handleServer 都在主线程），原样。

3. PlaceBlueprintMessage 改写点
   a. 消息改写：record 或 final 字段均可；encode / decode 原样（writeUtf / readUtf 上限 32、未知 rotation 回退 NONE、FluidDisplayMode.fromByte）；
      handle(IPayloadContext) + handleServer(msg, ServerPlayer)；
      decode 无按计数分配（K13 自查一遍写进报告）。
   b. 物品数据直读 → 访问器（C12）：
      stack.getTag().getString("blueprintId") → AbstractBlueprintItem.getBlueprintId(stack)，null 补 ""（与 1.20.1 缺键语义一致，SBN-010 同）；
      stack.getTag().contains("creatorName") / getString → stack.has(CREATOR_NAME) / VoidDimensionalBlueprintItem.getCreatorName。
   c. 建造蓝图物品（BuildBlueprintItem）三处 buildNbt → 组件逐项 set，键名对照 功能联动手册 NBT 键 → 组件表：
      blueprintName→BLUEPRINT_NAME、saveMode→SAVE_MODE（CaptureMode 本体，不再存 ordinal）、completionTime→COMPLETION_TIME、
      sourceType→SOURCE_TYPE、blueprintId→BLUEPRINT_ID、captureMin/Max→CAPTURE_MIN/MAX、tpX/Y/Z→TP_X/Y/Z、tpDimension→TP_DIMENSION、
      worldUuid→WORLD_UUID、worldName→WORLD_NAME、creatorName→CREATOR_NAME。
      投影蓝图分支的 src.contains("blueprintData") 复制：旧内联数据在 1.21 留在 custom_data（LegacyItemMigration 类注释），
      改为「源有 custom_data 且含 blueprintData → 复制到建造蓝图的 custom_data」；BuildBlueprintItem.restore 的 transmuteCopy 会带回去。
      判据：BuildBlueprintItem.restore(建造蓝图) 得到的物品与 1.20.1 语义一致（void_dimensional 12 个组件、project 整份组件去掉两个）。
   d. 网络：sendResult / sendPlacementCancelled / markPlacedAndSync 的 CHANNEL.send → BlueprintNetwork.sendToPlayer；
      markPlacedAndSync 里 sendBlueprintTo 原样。
   e. runCompletionCommand：createCommandSourceStack().withPermission(2).withSuppressedOutput() + performPrefixedCommand 在 1.21 原样可用（J45）。
   f. 判断顺序一个都不许挪：冷却 → 物品识别 → 次元归属 → 数据 → 已放置 → 存档归属 → 工程边界 → 距离 → 校验 → 领地预检 → 材料 / 物品 → 快照 → 日志 → 放置。
      尤其「领地预检必须先于任何材料、物品、文件状态修改」（1.20.1 注释原话），测试 t07 要证明。

4. 双端同步：放置只在服务端改世界，客户端看到的是原版方块同步 + S2C_PlacementProgressMessage（客户端体仍是 P5 桩）；
   物品替换后 ItemSyncUtil.syncHand 原样。报告第七节逐条自查。

5. 顺手：SBN010Tests、SBN011Tests 里 assertValueEqual 的参数顺序改成（实际, 期望, 名字）—— 以 javap GameTestHelper.assertValueEqual 的形参名为准，
   断言内容与条数不变（SBN-010 / 011 验收附注）。改完这两个文件的测试照旧全过；改动逐处计数进报告。
