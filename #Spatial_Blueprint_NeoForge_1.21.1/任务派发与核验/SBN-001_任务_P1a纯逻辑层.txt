三、已定方案
========================================================

总原则：逐文件照 1.20.1 搬，**逻辑、字段、NBT 键名、配置键名与默认值、lang 键一律不改**；只改 API。
每个文件搬完用 diff -w --strip-trailing-cr 和 1.20.1 源比对，残差（滤掉 import / 包名样板后）逐条列进报告「改了写法的调用」。

1. 配置系统（BlueprintConfig / GeneratedSubstitutionsConfig / ConfigRegistry）
   a. ForgeConfigSpec → net.neoforged.neoforge.common.ModConfigSpec（Builder / IntValue / BooleanValue / ConfigValue / ValueSpec 同名嵌套类）。
   b. 列表项：1.20.1 写法是 define("key", (List<String>) new ArrayList<>(...))，字段类型 ConfigValue<List<String>>。
      先 javap / 读 ModConfigSpec.Builder 源码确认 define(String, T) 对 List 默认值是否仍可用、是否 @Deprecated：
        - 可用且不带弃用警告 → 原样保留（优先，改动最小）；
        - 否则改 defineListAllowEmpty(路径, 默认值 Supplier, 新元素 Supplier, 校验 Predicate)，字段类型随之改 ConfigValue<List<? extends String>>，
          ConfigRegistry 与各调用点跟着改；报告写明选了哪条、为什么。
      不管哪条，toml 里的键名、注释、默认内容不许变（两条线的配置文件要能互相拷贝）。
   c. ConfigRegistry.accepts 里的 SPEC.getSpec().get(path) + instanceof ValueSpec + vs.test(candidate)：确认 NeoForge 同名 API 语义不变
      （那段注释说的「必须是 getSpec() 不是 getValues()」的坑在 NeoForge 里是否依旧成立，javap 看一眼写进报告）。defaultInt 用 getDefault() 同理。
   d. BlueprintConfig.onConfigReload(ModConfigEvent)：NeoForge 的事件总线不允许给抽象事件类注册监听（会在注册时抛异常，属于「编译能过、运行才错」）。
      ModConfigEvent 若为 abstract，改成在主类分别 addListener(ModConfigEvent.Loading) 与 addListener(ModConfigEvent.Reloading)，
      方法体保持原样（清缓存）。只对本 mod 的配置生效的判断如果 1.20.1 里有就照搬，没有就不加。
   e. 注册（主类构造器，用传进来的 ModContainer）：
        modContainer.registerConfig(ModConfig.Type.COMMON, BlueprintConfig.SPEC, "spatial_blueprint/spatial_blueprint.toml");
        modContainer.registerConfig(ModConfig.Type.COMMON, GeneratedSubstitutionsConfig.SPEC, "spatial_blueprint/block_substitutions.toml");
      注册前照 1.20.1 先 Files.createDirectories(FMLPaths.CONFIGDIR.get().resolve("spatial_blueprint"))（FMLPaths 在 net.neoforged.fml.loading）。
      类型保持 COMMON（与 1.20.1 一致；服务端权威靠 1.20.1 的「配置界面走网络」那一套，P3 再迁）。
      双端同步问题：本任务不引入任何客户端读配置的代码，不产生新的不同步点；报告里照「客户端和服务端会不会不同步」自问一遍写一句结论。
   f. ConfigRegistry 引用的全部配置项必须在 BlueprintConfig 里存在；1.20.1 的 BlueprintConfig 若引用了不在本清单里的类（网络、客户端等），
      那一条按迁移桩处理（见 3.10），不许为了编译扩大清单。

   1.20.5 起 NbtUtils.writeBlockPos 写成 IntArrayTag [x,y,z]，readBlockPos 改成 readBlockPos(CompoundTag 父标签, String 键) → Optional<BlockPos>
   （云端未 javap，执行前核实）。而 1.20.1 线存盘的 fixedStartPos / fixedEndPos / relP1 / relP2 / origin / size / anchor 全是 {X:,Y:,Z:} 复合标签。
   已定：
     - NbtCompat.writeBlockPos(BlockPos) → 写 1.20.1 的 {X,Y,Z} 复合标签（两条线的文件格式保持一致，也不用等 P4 的 DataFixer）；
     - NbtCompat.readBlockPos(CompoundTag 父标签, String 键) → 同时接受 {X,Y,Z} 复合标签与长度 3 的 int 数组；缺键返回 null，调用方原来的缺键语义不变。
       （1.20.1 的 NbtUtils.readBlockPos(getCompound(缺键)) 返回 (0,0,0)；凡原代码依赖这个 0 的地方，调用方写 Objects.requireNonNullElse(..., BlockPos.ZERO)，保持原行为。）
     - BlueprintData 与 ProjectData 里全部 NbtUtils.writeBlockPos / readBlockPos 调用改走 NbtCompat。报告列出每一处。
   这是 1.21.1 独有的新类，类头写一句为什么存在（上面两行的意思），云端验收时登进功能联动手册。
