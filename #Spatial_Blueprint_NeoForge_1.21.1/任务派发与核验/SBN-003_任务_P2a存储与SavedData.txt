========================================================
三、已定方案
========================================================

总原则同前：逻辑、字段、NBT 键名、文件名规则、SavedData 名（SAVE_KEY / DATA_NAME）一律不改，只改 API 与下面点名的地方。
每个文件 diff -w 残差逐条进报告「改了写法的调用」。

1. FMLPaths / ServerLifecycleHooks
   FMLPaths → net.neoforged.fml.loading.FMLPaths（SBN-001 已用过）。
   ServerLifecycleHooks → net.neoforged.neoforge.server.ServerLifecycleHooks（javap 核对，J17）。

2. SavedData（7 个类同一套改法）
   a. save(CompoundTag) → save(CompoundTag, HolderLookup.Provider)；load(CompoundTag) → load(CompoundTag, HolderLookup.Provider)（provider 暂不用也照签名收）。
   b. getDataStorage().computeIfAbsent(X::load, X::new, KEY) → computeIfAbsent(new SavedData.Factory<>(X::new, X::load, null), KEY)
      （第三参数 DataFixTypes 传 null，与 HD 一致；J18 核对 Factory 构造器）。
   c. 不改 SAVE_KEY / DATA_NAME，也不改存盘结构 —— 1.20.1 世界升级上来，data/*.dat 要能原样读回。
   d. WorldIdentity 里「computeIfAbsent 之后手动 setDirty + getDataStorage().save()」那段照搬（1.21.1 DimensionDataStorage#save() 仍在，J18）。
   e. SBUndoData 的 BlockState 读写（NbtUtils.readBlockState(BuiltInRegistries.BLOCK.asLookup(), …) / writeBlockState）照 SBN-001 的口径保留；
      快照里的方块实体 / 实体 NBT 是写入时的版本格式，不做升级（见 4.d）。

3. D8：材料复合键组件化（迁移计划书 D8 拍板原文为准）
   a. MaterialKey.make(String id, CompoundTag raw) / idOf / hasTag / normalize / canonical / digest 保持不变（纯字符串 / NBT 逻辑）。
   b. MaterialKey.of(ItemStack) → MaterialKey.of(ItemStack, HolderLookup.Provider)：
      空栈返回 ""；否则 raw = 该栈组件补丁按 DataComponentPatch.CODEC、以 provider.createSerializationContext(NbtOps.INSTANCE) 编码成的 CompoundTag
      （补丁为空 → null）；return make(id, raw)。去掉 SBN-001 的桩。
      **一致性要求**：这个 raw 必须与 ItemStack.save(provider) 写出的 "components" 子标签逐字相同（t02 断言）——
      实体身上的物品（MaterialList.mergeItemCount 读的是实体 NBT）和手里的物品必须算出同一个键。
      若 javap / 实测发现两者编码不同，停下来在报告里写清差异，按「以 ItemStack.save 的 components 为准」统一，并写进「任务书出入」。
   c. pruneNoOps：对键 "minecraft:block_entity_data" 的 compound 与旧 "BlockEntityTag" 同样处理（删掉其中的 id 再递归剔除空结构）。
      补丁里「移除某组件」的标记键（形如 "!minecraft:xxx"，值为空 compound）**不许被当成空结构剔掉** —— 它表示「这个物品没有该默认组件」，
      是真差异。pruneNoOps 遇到以 "!" 开头的键跳过（t01 用一个移除了默认组件的物品验证键与普通物品不同；若找不到自然会产生移除标记的原版物品，
      用 stack.remove(DataComponents.XXX) 人为造一个）。
   d. MaterialList.mergeItemCount：raw 取 item.components（compound，1.21 格式）；没有再取 item.tag（旧格式）；
      去掉 SBN-001 的 SB-TODO(P2)。count 双读（count / Count）保留。
   e. BlueprintConfig.materialSpaceIgnoredNbtKeys 默认值由 ["RepairCost"] 改为 ["RepairCost", "minecraft:repair_cost"]，注释不动。
      MaterialKey.ignoredKeys() 的「配置未加载」回退值同步改成这两项。
   f. MaterialList.buildDisplayStack(String key, CompoundTag tag) → buildDisplayStack(String key, CompoundTag tag, HolderLookup.Provider provider)：
      tag 非空时按 DataComponentPatch.CODEC 用同一个 ops 解析，成功就 stack.applyComponents(patch)；解析失败（旧格式 tag）→ 返回无组件的普通栈，
      不抛异常、不刷日志（旧格式键的迁移在 P4）。getDisplayStack 同步加 provider 参数。去掉 SBN-001 的桩。
      上一行写 // SB-TODO(P4): 旧格式 tag 摘要的材料键随 DataFixer 迁移（D2 / D8）—— 放在「解析失败」分支处，只写一条。
   g. MaterialSpace.displayStack(String) 同步加 provider 参数，透传给 buildDisplayStack。其余 MaterialSpace 逻辑原样。

4. BlueprintStorage / ProjectStorage
   a. 目录、文件名规则、原子写（writeCompressedAtomic）、摘要缓存、listSummaries 原样。
   b. 读文件走 SafeNbtIo（1.20.1 若已如此则原样）；坐标读写一律 NbtCompat（1.20.1 的 NbtUtils.readBlockPos(getCompound(…)) 那两处，见 BlueprintStorage 约 519–521 行），
      缺键语义按 SBN-001 三.4 保持。
   c. BlueprintStorage.load 读出的是 BlueprintData.deserialize 的结果；不在这里插 DataFixer（P4 在 deserialize 之前插，SBN-001 已留桩）。
   d. 旧数据：1.20.1 世界升级上来的 SBUndoData 快照、MaterialSpace 里按旧 tag 摘要的键、旧蓝图文件里 materialList 的旧键，本任务都原样读写、不迁移；
      报告里列出「会原样带过来的旧格式数据」清单（按类 + 字段），给 P4 用。

5. 主类
   commonSetup 里按 1.20.1 顺序接上 BlueprintStorage.init()、ProjectStorage.init()，删掉 SBN-001 对应的那条 SB-TODO(P2): Storage.init。
   其余 SB-TODO 不动。
