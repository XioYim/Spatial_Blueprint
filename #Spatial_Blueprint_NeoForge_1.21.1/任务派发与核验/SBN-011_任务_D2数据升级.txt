一、背景与目标
========================================================

D2（用户拍板）：1.20.1 蓝图文件与玩家手上的旧蓝图物品都要能读，按 DataVersion 走原版 DataFixer 升级方块状态 / 方块实体 / 实体 / 容器物品。
物品那半边 SBN-004 已做（LegacyItemMigration）；本任务做**数据那半边**，放在放置引擎（SBN-012）之前，让放置拿到的永远是 1.21 格式。

云端已查的数据入口：
  a. 蓝图文件 —— 所有读取（BlueprintStorage.load、ProjectStorage、上传 handleAssembled、蓝图材料请求）都经过 BlueprintData.deserialize；
     那里已留 SB-TODO(P4) 桩。1.20.1 的 serialize 固定写 MinecraftDataVersion = 3465；1.21.1 写当前版本（SBN-001）。
     文件是 litematic 结构：Regions.<名>.BlockStatePalette（方块状态 NBT {Name, Properties}）、TileEntities（完整方块实体 NBT，含 id）、Entities（完整实体 NBT，含 id）。
  b. 材料键（D8 遗留）—— 蓝图文件里 SpatialBlueprintData.materialList 的键与 keyTags：1.20.1 按旧物品 tag 算摘要（键形如 id#摘要，keyTags 存旧 tag）；
     MaterialList.buildDisplayStack 旧格式分支已留 SB-TODO(P4) 桩。
  c. 世界存档里的 MaterialSpace（SavedData）—— 同样的旧键 + tagRegistry 旧 tag；1.20.1 世界升级上来原版 DataFixer 不碰 mod 的 SavedData。
  d. 世界存档里的 SBUndoData（SavedData）—— 撤销快照里的方块状态 / 方块实体 NBT / 实体 NBT 是写入时的格式（SBN-003 报告已列）。

本任务结束时：1.20.1 格式的上述四类数据载入即升级为 1.21 格式；1.21 格式的数据原样不动。放置引擎在 SBN-012。

========================================================
三、已定方案
========================================================

1. util/LegacyDataFixer（纯函数、服务端 / 客户端都可调，不读配置不读文件）
   a. 版本口径：public static final int LEGACY_DEFAULT = 3465（1.20.1）；public static int current() = SharedConstants.getCurrentVersion().getDataVersion().getVersion()。
      public static int effectiveFrom(int readVersion)：readVersion <= 0 → LEGACY_DEFAULT（缺键视为 1.20.1：本 mod 只有 1.20.1 一条旧线）；其余原值。
      public static boolean needsFix(int from)：from < current()。**from ≥ current 一律不动**（不降级；比当前还新的数据原样保留）。
   b. 四个升级函数，签名形如 CompoundTag fixBlockState(CompoundTag tag, int from) / fixBlockEntity / fixEntity / fixItemStack：
      DataFixers.getDataFixer().update(References.BLOCK_STATE / BLOCK_ENTITY / ENTITY / ITEM_STACK, new Dynamic<>(NbtOps.INSTANCE, tag), from, current())
      （DataFixTypes 没有这四种的包装，直接用 DataFixer.update，J44；SBN-004 t04 已用同一写法升级 ITEM_STACK）。
      结果不是 CompoundTag 或抛异常 → **返回原 tag**（copy），调用方计数；不抛到调用方外（一个坏条目不能让整份蓝图读不出来）。
      方块实体 / 实体 NBT 没有 id 字段时不调 DataFixer（它靠 id 选修复器），原样返回并计数。
   c. 材料键迁移：public static String migrateMaterialKey(String key, @Nullable CompoundTag legacyTag, int from)：
      键不带 '#'（MaterialKey.hasTag 为 false）或 legacyTag 为 null → 原样返回；
      否则组 {id: MaterialKey.idOf(key), Count: 1b, tag: legacyTag}（1.20.1 物品格式，C8 / K8 口径）→ fixItemStack → 取结果的 components（缺则 null）
      → MaterialKey.make(id, components) 作为新键。附带返回新键对应的「规范化后的新 components」给调用方写 keyTags / tagRegistry
      （形态自定：返回 record，或拆两个方法；报告写明）。
   d. 调用方累计的「未能升级条目数」在 deserialize / load 结束时若 > 0，记一条 WARN（带蓝图名 / 存档数据名与条数），不逐条刷日志。

2. BlueprintData.deserialize（删掉 SB-TODO(P4) 那条桩）
   data.dataVersion 仍记文件里读到的原值（字段语义不变）；int from = LegacyDataFixer.effectiveFrom(data.dataVersion)；
   needsFix(from) 时：BlockStatePalette 每项先 fixBlockState 再 readPaletteEntry；TileEntities 每项 fixBlockEntity 后再进 tileMap
   （litematic 的 TE 坐标 x / y / z 是相对坐标，升级前后保持；升级后按原逻辑覆盖成世界坐标）；Entities 每项 fixEntity 后再建 EntityEntry；
   materialList 走三.3 的带版本重载。needsFix 为 false 时逻辑与现在逐字相同。
   serialize 不改（仍写当前版本）—— 升级后的蓝图一旦被写回，就是 1.21 格式文件。

3. MaterialList
   a. 新增 public static MaterialList deserialize(CompoundTag tag, int from)；原 deserialize(CompoundTag) 保留，等价于 from = current()（不迁移），其余调用方不动。
   b. needsFix(from) 时对每个键调 migrateMaterialKey：新键计数合并（两个旧键映射到同一新键 → 数量相加）、keyTags 换成新 components；无 tag 的键原样。
   c. buildDisplayStack 里「解析失败（旧格式 tag）→ 普通栈」的分支保留（防御），删掉那条 SB-TODO(P4)，注释改成「旧键已在载入时迁移（SBN-011），这里只兜底」。

4. MaterialSpace
   save 写一个 int 字段 dataVersion = current()；load 时读不到该字段 → from = LEGACY_DEFAULT，needsFix 时把 pool / 次元袋 / consumed 等所有按材料键索引的表
   与 tagRegistry 一起迁移（同一新键合并数量），迁移发生过就 setDirty()。有字段且 ≥ current → 原样。字段名与已有键不冲突（报告写明）。

5. SBUndoData
   同 4 的版本标记口径；旧数据载入时快照里的方块状态 NBT → fixBlockState、方块实体 NBT → fixBlockEntity、实体 NBT → fixEntity；迁移发生过就 setDirty()。
   撤销 / 冷却规则不改。

6. 不在本任务：放置引擎（SBN-012）；导入器（litematic / schem / schematic 的客户端转换在 P5 / P6，转换结果经上传进 deserialize，天然被本任务覆盖）；
   ProjectData 的非蓝图字段（无物品 / 方块实体数据）。
