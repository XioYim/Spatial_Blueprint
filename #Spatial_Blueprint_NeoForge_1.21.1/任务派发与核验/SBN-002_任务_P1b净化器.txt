========================================================
一、背景与目标
========================================================

BlueprintSanitizer（1.20.1 线 util/BlueprintSanitizer.java，1317 行）是上传 / 捕获两条路径的安全闸：
非法方块、容器里的非法物品、告示牌 / 讲台书里的命令点击事件、刷怪笼生成数据、白名单外实体、超大 / 超深 NBT。

它全部靠「NBT 长什么样」来判断。1.20.5 起物品存储从 {id, Count:byte, tag:{...}} 改成 {id, count:int, components:{...}}，
容器组件里的物品还多包一层 {slot, item:{...}}。原样搬过来**能编译、测试也可能过，但会漏检或留下读不回来的残片**，所以单独一个任务。

目标：搬进 1.21.1，且对 1.21.1 真实产出的 NBT 行为与 1.20.1 对旧格式的行为一致（同一种危险内容，两边同样被判、同样被清）；
旧格式（tag / Count）照样认（P4 的 DataFixer 之前，旧文件原样进来也不许放行）。
另按 D9 把 trial_spawner / vault 纳入默认禁捕，并清试炼刷怪笼的生成配置。

========================================================
三、已定方案
========================================================

总原则同 SBN-001：逻辑、字段、键名、lang 键不改，只改 API 与下面点名的格式适配。
每一处格式适配都**同时认新旧两种格式**（1.21 的 count / components，旧的 Count / tag），宁可多判危险不可漏判（fail-closed）。
diff -w 残差逐条列进报告「改了写法的调用」。

1. 原样搬、预期零改动的部分（有改动就写进报告）
   exceedsMaxDepth、estimateNbtBytes、checkNbtBudget、effectiveNbtBytes、containsIllegalItemDeep（它只认键名为 id 的字符串，
   1.21 物品与实体仍是这个约定，组件里嵌的物品也一样会被 BFS 走到）、isIllegalItemId、HARDCODED_ILLEGAL_ITEMS、
   告示牌四件（hasSignCommandClickEvent / sanitizeSignMessageJson / findSignRunCommand / sanitizeSignJson），
   UploadScan / ScanEntry / ScanEntity / scanBlueprintData / countBlocks / scanBlockList、sanitizeForUploadInPlace 及其 strip* 系列、
   实体白名单 / ALLOWED_MOB_ENTITIES / isEntityAllowed / filterEntitiesInPlace、sanitizePaintingNbt、坐标范围、
   isIllegalBlock / isIllegalBlockId / removeIllegalMaterialsInPlace / enforceTemplateFieldRules、
   entityHasIllegalItems / findEntityWithIllegalItems（Entity.save(CompoundTag) 与 getEntitiesOfClass 在 1.21.1 仍在，编译为准）。
   告示牌：1.21.1 的 front_text / back_text.messages 仍是 JSON 字符串、点击事件键仍是 clickEvent（1.21.5 才改），
   s05 用真实 SignBlockEntity 存出来的 NBT 验证；若不是，按实际改并报告。

2. 容器组件的「槽位包一层」（stripContainers / listHoldsItemEntries）
   1.21 容器组件（minecraft:container）存成 [{slot:0, item:{id, count, components}}, …]。1.20.1 的 listHoldsItemEntries 只认
   「列表元素本身是物品」，于是这种列表会被当成普通列表往里递归，只删掉每个元素里的 item，留下 [{slot:0}, …] 残片 ——
   这个组件整条解码失败，方块实体 / 物品读回来会报错或静默丢数据。
   已定：listHoldsItemEntries 对元素的判定改为「isItemEntry(元素) 或 元素有 compound 键 item 且 isItemEntry(元素.item)」，
   命中即整条列表删除（与 1.20.1「整袋倒掉」口径一致）。isItemEntry 本身不改（id + Count 或 count，1.20.1 已兼容小写）。
   这同时覆盖一条 1.21 才有的夹带路径：方块实体 NBT 的 components 子标签里塞 minecraft:container，
   加载时会被 applyImplicitComponents 填进潜影盒 —— 改后它会被整条删掉。s02 必须验证这条。

3. 蜂箱键名
   1.21.1 蜂箱存 bees（小写，元素里是 entity_data），1.20.1 是 Bees / EntityData。
   STRIP_SKIP_KEYS 改为 Set.of("Book", "Bees", "bees")。以 s08 里真实 BeehiveBlockEntity 存出的键名为准。

4. 讲台书（hasDangerousBlockNbt / bookContainsCommand）
   1.20.1：Book.tag.pages（字符串列表）+ Book.tag.filtered_pages（compound）。
   1.21.1：Book.components."minecraft:written_book_content".pages，每页是一个可过滤文本（预期编码为 {raw:"<JSON>", filtered:"<JSON>"}，
   也可能是裸字符串）；书与笔（minecraft:writable_book_content）是纯文本，没有点击事件，不用查。
   已定：抽一个私有方法「从 Book 取出全部页面 JSON 字符串」，同时收：旧 tag.pages / tag.filtered_pages 的全部值，
   新 components.written_book_content.pages[] 里的裸字符串、raw、filtered。hasDangerousBlockNbt 与 bookContainsCommand 都改走它，
   applySafetyStripInPlace 里「Book 含命令就整本移除」的条件从「book.contains("tag")」改为「bookContainsCommand(book)」（新旧格式都能触发）。
   s04 用真实 ItemStack（WRITTEN_BOOK + WrittenBookContent 组件）存出的 NBT 验证；报告里贴出真实页面编码的形状（证据/nbt_样本.txt）。

5. 展示框物品净化（sanitizeItemFrameContentInPlace）
   1.20.1：安全物品只保留 id + Count(byte)，丢 tag。原样搬到 1.21 会写出 Count 而不是 count，组件也没丢干净的保证。
   已定：安全物品重建为 {id, count:int}，count 取 count（int）→ 没有再取 Count（byte）→ 都没有记 1；components 与 tag 都丢。
   危险物品整条删除（不变）。s06 验证重建后的 Item 能被 ItemStack.parse(provider, tag) 解析成功且没有组件。

6. 试炼刷怪笼（D9 净化兜底）
   1.21.1 的 trial_spawner 方块实体键（预期）：spawn_data、normal_config、ominous_config（后两者里有 spawn_potentials）。
   已定：hasDangerousBlockNbt 在刷怪笼判断之后追加：spawn_data 为非空 compound，或 normal_config / ominous_config 任一存在且非空 → 危险；
   applySafetyStripInPlace 追加 remove 这三个键。以 s07 真实 TrialSpawnerBlockEntity 存出的键名为准，不一致按实际改并报告。

7. 刷怪笼（spawner）：SpawnData / SpawnPotentials 键名 1.21.1 不变（预期），s07 顺带用真实 SpawnerBlockEntity 核对。

8. D9 默认禁捕（BlueprintConfig）
   excludedBlocks 默认列表末尾加 "minecraft:trial_spawner", "minecraft:vault"；excludedItems 默认列表末尾加同样两项。
   只改这两处默认值，注释与其它项一字不动；报告写清这是有意与 1.20.1 分叉（迁移计划书 D9）。
   注意：已存在的 toml 不会自动加上，这是 ModConfigSpec 的正常行为，不需要写迁移逻辑。

9. S2C_IllegalBlocksListMessage 的 record 与 BulkMaterialConverter
   UploadScan 的 conversions 字段与 BulkMaterialConverter.collectConversions 用到 S2C_IllegalBlocksListMessage 的嵌套 record。
   已定：新建 network/s2c/S2C_IllegalBlocksListMessage.java，**只放 1.20.1 里的全部嵌套 record**（IllegalBlock / SpecialEntity / TargetItem /
   ConversionEntry / BoxEntity / ProtectedChunk，字段逐字照搬），类体里不写编解码与 handler；类声明上一行写
   // SB-TODO(P3): S2C_IllegalBlocksListMessage 消息本体（StreamCodec / handler）。
   record 若引用了 1.20.1 的其它类型（例如 FriendlyByteBuf 的读写方法），只搬 record 声明，方法留给 P3，按迁移桩写注释。
   BulkMaterialConverter.collectConversions 去掉注释恢复原样，删掉 SBN-001 的那条桩。

10. 发现但不改（写进报告「与 1.20.1 同样存在的问题」段，由云端问用户是否两条线一起修）
   a. armorStandHasEquipment / nonEmptyItemList 只看列表是否为空，而盔甲架的 ArmorItems / HandItems 空槽也存成 {}，
      列表恒为 4 / 2 个元素 → 「带装备」恒为真。s09 用真实 ArmorStand 存出的 NBT 核实并记录，不改代码。
   b. 容器方块实体的 LootTable（1.21.1 预期键名 LootTable / LootTableSeed）没有任何一条路径清理：
      捕获一个没开过的地牢箱子，蓝图可反复放置 → 每次放出来都能重新生成战利品。s10 用真实箱子 setLootTable 后存出的 NBT
      记录键名与 stripItemContents 之后是否仍在，不改代码。
