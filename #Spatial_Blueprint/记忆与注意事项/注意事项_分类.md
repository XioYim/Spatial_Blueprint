### T1 · 这是什么

- Spatial Blueprint —— Minecraft 1.20.1 / Forge 模组，modid `spatial_blueprint`，源码 219 个 `.java`（2026-09-24 数）。
- 工程 Forge 版本 `forge_version=47.4.10`（`gradle.properties`）；实机测试服务端 `XioYim_Server` 为 Forge 47.4.16。
- **协议版本 = mod 版本**；当前版本见 `gradle.properties`（构建号）与 `项目记忆.md`「环境现状」当前部署（jar 字节 / SHA256 / 三端），发版只更新那边，这里不跟数字（跟了必烂）。

### T2 · 构建与警告基线

- 验编译：`.\gradlew.bat compileJava --offline --rerun` → 要 `BUILD SUCCESSFUL`。增量 `classes` 会 UP-TO-DATE、一条不打印，验收一律带 `--rerun`。
- **警告基线 20 条**（按 `\.java:\d+:` 计数 —— 本机 javac 输出中文，按 `warning` 数恒为 0）。2026-09-24 由 21 改 20：e64 起实测稳定 20 条（全为 `[removal]`），e63 清理前后的具体漂移点未查。
- 构建：`.\gradlew build --offline` → `build\libs\spatial_blueprint-<版本>.jar`；离线证书问题加 `-Dnet.minecraftforge.gradle.check.certs=false`。

### T3 · 网络协议与发版

- **发版必须 bump mod_version** —— 同一版本号下出现过两个不同产物（经过见开发日志），只看版本号分辨不出手上是哪份。**末位到 9 就进位**（2026-09-25 用户拍板）：`x.y.9` 的下一版是 `x.(y+1).0`，不出现 `x.y.10`；当前 `2.7.38` 已超过 9，下一次部署直接进 `2.8.0`。
- **新增消息必须走 `BlueprintNetwork.c2s()` / `s2c()`，且只能追加在 `register()` 末尾。** 注册顺序就是线上的消息序号，插队 / 删除 / 改方向都必须 bump mod_version 并同时更新双端。方向标反的后果是玩家一发那条消息就被踢下线（「Illegal packet received」），不是静默失败。
- 新增 S2C 字段：encode/decode 对称、客户端缓存整份替换、wire 变了 bump mod_version。
- **`S2C_LibrarySyncMessage.writeSummary / readSummary` 被 `S2C_VoidBagSyncMessage` 复用**：改 `BlueprintSummary` 字段 = 两条 S2C 同时 wire 变，bump 一次即可，但回归要连虚空袋材料空间一起测（SB-009 / 归档 e39、e42）。

### T4 · 客户端 / 服务端边界

- **上传判定用服务端配置**，勿用 `S2C_ConfigSyncMessage.slotLimitFor` 客户端镜像。
- **服务端读蓝图数据一律用 `getBlueprintDataServer` / `getMaterialListServer`。** `FMLEnvironment.dist` 是物理端，单人与局域网主机上等于 CLIENT，拿它当逻辑端用就是 H3 那个坑。tooltip 是唯一可以按物理端分派的场景（`getMaterialListForTooltip`），别照抄到别处。
- 客户端会话缓存新增时，**必须挂 `ClientPlayerNetworkEvent.LoggingOut` 复位**，否则上个服的状态会带进下个服。例外只有 `ClientPreviewSettings`（本地 json 持久化设置）。
- **改完主类或任何非 client 包的类，验产物不验源码**：`javap -p -c SpatialBlueprintMod.class | grep net/minecraft/client` 必须 0 命中 —— 编译通过不是证据，内联 lambda 会把 `Screen` 带进主类的 synthetic 方法签名，FML 在 CONSTRUCT 阶段就会让专服起不来。客户端类型只能出现在 `client/`、`gui/` 包，或带 `@OnlyIn(Dist.CLIENT)` 的成员上。（`javap -v` 的类级注解在输出末尾，别用 `head`/`tail -20` 取。）

### T5 · 权限与归属

- **归属判断一律用 `ownerUuid`，不要用 `creatorName`** —— 后者是捕获当时的玩家名，改名就对不上。唯一例外是无主旧数据（`ownerUuid` 为空）的**可见性**回退，见 `BlueprintLibraryScreen.isMineForListing`；**权限判断不许放宽**，无主一律判否。
- **会写别人蓝图文件的操作一律走 `BlueprintValidator.canManageBlueprint`**（主人或 OP；无主蓝图只有 OP 能碰）。`isCreative()` 只表示「这是蓝图库管理场景」，不等于有权动这一份，两道都要过。次元蓝图删除另有自己那套三段式判定，别用本入口顶掉它。
- WorldOwn 归属判定禁逐条 INFO（高频）。
- **蓝图传送权限只有 `TeleportPermissions.canTeleport` 一处**（OP / 创造 / `/sb tpperm` 名单），工程与次元两条传送消息共用，客户端只拿 `ClientTeleportPermCache` 置灰按钮；不要再按蓝图 / 按类型加第二道权限门 —— SB-009 就是删掉这种分叉（安全坐标 + 生存放行开关），见归档 e39。另有限流一处（`tryAcquireTeleport`，两类共用 6 秒内存态，防连点刷落地保护效果，见 e77）——限流不是权限，它的存在不代表可以再加权限门。
- **凡是从手持物品 NBT 取 blueprintId 再删文件 / 清次元袋 / 写盘的 C2S，服务端必须自己校验存档归属 + 主人**（照 `C2S_VoidRecaptureMessage` 的顺序：存档 → 文件在否 → 主人），界面入口拦过、客户端有二次确认都不算 —— `C2S_VoidResetMessage` 就是漏网实例（SB-014 G1，见 e64 / e65）。

### T6 · 世界改动 / 捕获与净化

- **任何会改动世界方块的路径，创造模式是否受领地检查一律看 `DENY_CREATIVE_PLACEMENT_IN_PROTECTED_AREA`**（默认 true），不要硬编码 `!isCreative()`。已接入：放置两处 + 次元捕获 + 虚空重捕获。例外是放置侧的「结构冲突预检」（挡道方块），那个跟领地无关，只看游戏模式是对的。
- 三种超限语义不同：单体体积/深度 → 清 NBT 保留方块；体积总量 → 拒收。捕获路径刻意无限制（见 C2）。
- **两个 strip 方法分工别搞混**：`stripDangerousBlockNbt` 无条件倒容器（上传净化、`effectiveNbtBytes` 用它）；`stripDangerousBlockNbtKeepContents` 保留容器（次元蓝图捕获用）。安全项两者都做，共用 `applySafetyStripInPlace`。给次元蓝图加容器清理 = 回归。
- **次元蓝图只有 SAFE 一条路，任何人一样，OP 不豁免**：服务端 `CaptureAreaMessage` 对 `clearAfterCapture && effMode != SAFE` 直接拒；非法方块 / 方块实体 `hasDangerousBlockNbt` / 实体 `findEntityWithIllegalItems` 三道预扫任一命中整单拒，都在清世界之前。**捕获预扫与扫描报告 `C2S_RequestIllegalBlocksMessage` 必须用同一组判定**（`entityHasIllegalItems` 等），报告标危险的服务端必拒、报告没标的必放，否则玩家没法自己清理。给次元蓝图加任何净化 / OP 放行 = 回归。
- FORCE 模式对次元蓝图不可达：`BlueprintReportScreen` 的 OP 按钮会把 category 强制覆盖成 `create`/`reward`。别再设计依赖「次元 + FORCE」的方案。
- 深 JSON 靠体积检测封顶（`maxBlockEntityNbtBytes`），不是靠 65535 —— 两个阈值同时是两套防线。`catch(Throwable)` 保持（收窄会让 OOM 冒泡到网络线程被静默吞）。
- **任何净化 / 删方块 / 倒容器之后必须重算 `materialList`**（`MaterialList.fromBlueprintData`），沿用净化前的清单会多算；奖励蓝图的 ✎ 提取同理先生成再剔非法（SB-010 复制分支、SB-011）。

### T7 · Create 胶水与盒型实体

- **Create 胶水的 `From`/`To` 是相对 `Pos` 的偏移，不是世界坐标**（存盘 `bb.move(-pos)`，读盘 `+pos`，`Pos` = 盒底中心）。捕获几何一律取 `entity.getBoundingBox()`；放置写回 `Pos=(cx, minY, cz)`、`From=lo−Pos`、`To=hi−Pos`。把 From/To 当世界坐标就是 2.6.0~2.6.3 那个「一个胶水都捕不到」的坑。
- **盒型实体（From/To 角点）的坐标变换走 `BlueprintTransform.cornerX/cornerZ`，公式不带 `-1`。** 方块索引跑 0..size-1，角点跑 0..size，两套公式不能混用 —— 混用的表现是整个盒子偏一格。旋转后 From/To 会对调，**必须重新按 min/max 规范化**，否则写出反向 AABB。新增这类实体只要往 `BOX_ENTITIES` 配置里加 ID，不要在代码里引用对方 mod 的类。

### T8 · 配置与界面

- 配置界面一律走 `ConfigAccess`（服务端镜像 + 提交），不直写本地 toml；列表/数字快照刷新按 `ClientConfigMirror.snapshotVersion`。
- BuildTime 档位仅客户端显示估算（PointSelectionScreen），服务端权威，属可接受显示不一致，暂不投影。
- **查 `ValueSpec`（范围/默认）用 `SPEC.getSpec().get(path)`，不是 `getValues()`** —— 后者那张表放的是 `ConfigValue`，`instanceof ValueSpec` 永远不中，兜底分支会静默放行。只要默认值，直接 `value.getDefault()`，不用查表。

### T9 · 文本与提示

- **lang 占位符一律 `%s` / `%1$s`**，原版 `TranslatableContents` 不认 `{0}`，会原样画出来。
- **`S2C_OperationResult` 的主键（messageKey）在客户端不带参数渲染**：正文含 `%s` 的键不能当主键发，会把 `%s` 原样画出来。要带参数就主键用无参键、参数走 detail（`new S2C_OperationResult(false, key, detailKey, args)`），与领取 / 保存布局 / 删子工程路径同一约定（SB-005 报告发现，见开发日志 e10）。
- **所有报错提示一律用 ErrorToast 横幅**，不要用 `player.displayClientMessage()` / `sendSystemMessage()` 发到聊天栏：有宿主界面时 Screen 实现 `ErrorToastSupport`、在 `render()` 开头早返回渲染；无宿主界面时 `Minecraft.getInstance().setScreen(new ErrorToastScreen(message))`（任意点击 / ESC 关闭，不暂停游戏）。接入细节与现状口径见 C1。成功类通知可以走聊天栏，但 `S2C_OperationResult` 的成功分支会**关闭** `PointSelectionScreen` / `PlacementScreen`，不想关界面就别用它。

### T10 · 推送与 NBT 规则

- **服务端把蓝图发给客户端，只能走 `BlueprintNetwork.sendBlueprintTo`** —— 序列化一次、压缩一次、按 `S2C_BlueprintChunkMessage.CHUNK_SIZE` 切片，一个 chunk 也分片、没有 size 分支；超 `MAX_TOTAL_CHUNKS`(256) 只记 warn 不发。`S2C_BlueprintDataMessage` **故意保留**（类 + 注册 + 范围校验都在），但它是整包发送、超 1 MB 会在 decode 被拒 —— 看到 `new S2C_BlueprintDataMessage(` 出现在发送位置就是回归（曾经有六处这么干，大蓝图玩家看到空预览、得重开蓝图库下载一次）。
- NBT 预算规则句：三种超限语义、两个 strip 方法分工见 T6；原理与理由见 C2。

### K2 · 一、本机环境

- **改 UTF-8 文本不要用 PowerShell**：禁用 `Set-Content` / `Add-Content` / `(Get-Content -Raw) -replace ... | Set-Content` 处理 lang / json / md / py 等（会破坏编码）；改用 Write / Edit 或 .NET UTF-8 无 BOM 写。
- **本机 `python` / `python3` 是 Windows Store 存根**（`python --version` 输出空字符串、脚本静默失败、无报错）—— 改用 `node`（v24）：`fs.readFileSync(p, "utf8")` / `fs.writeFileSync(p, s, "utf8")`（Node 的 "utf8" 不带 BOM，正是要的）。
- **含 Windows 路径 / 反斜杠的脚本一律 Write 落成 `.js` 再 `node <file>`**：`node -e` 与 `node - <<'EOF'` 都会把脚本里的反斜杠吃掉一层（`\s`、`\.` 变 `s`、`.`，静默不命中）。纯字面串、不含转义字符的脚本除外。
- **Bash 工具的 heredoc 会被未配对单引号打断**（如 `entity's`、`task's`）；含中文或撇号的长文本用 Write 落成脚本文件再执行，不走 heredoc、也不走 `node -e`。例外：纯追加长文本到 md 用 `cat >> file <<'EOF'` 是稳的（内容里没有未配对英文撇号时）。
- **本工作区有多个写入方，mtime 不能用于归因**；大动作前按安全手册做带时间戳的备份；编码类操作先小样本探测（写 1 行读回验证）再整文件处理；改完 JSON 一定用解析器验一遍。
- **PS 5.1 `Select-String` 即使零命中 `$?` 仍为 `$true`**（只在出错时为假）：`... | Select-String "x"; if ($?)` 永远走真分支；判 javap 有无 `minecraft/client` 引用改用 `$out -match "minecraft/client"` 写法（SB-013 中途误报一次，见 e60）。

### K5 · 任务执行易错点

- **`X.get()` → `ConfigAccess.get(X)` 文本替换要数括号**：原 `.get())));` 的四个 `)` 里有一个属于被删掉的 `.get(`，直接文本替换会少一个右括号导致编译错；替换后务必逐行数外层括号或改完即编译（SB-012 中途撞上，见 e58）。
- **mtime 窗口时间用备份脚本打印的开工时刻**：不能凭记忆写派发时间——写错窗口会把上一个任务的文件也算进来；每次开工前先确认备份脚本打印的精确时间戳（SB-012，见 e58）。
- **会触发全盘扫描 / 重 IO 的请求类 C2S（无参或轻参）必须带同人冷却**，也不要在 handle 里作废缓存（写盘处自己会作废）—— `C2S_RequestLibraryMessage` 是漏网实例，对照 `C2S_RequestBlueprintDataMessage` 的 500ms 冷却（SB-014 A2，见 e64）。

### C1 · 常项参考：报错横幅（ErrorToast）接入（按现状订正）

**组成**：`gui/ErrorToast.java`（无状态渲染工具，单方法 `render()`）；`gui/ErrorToastSupport.java`（接口 `setErrorToast(Component)`）；`gui/ErrorToastScreen.java`（无宿主界面时的独立横幅，关闭后回原界面 / 游戏）；`network/s2c/S2C_OperationResult.java`（服务端失败结果**自动**调 `setErrorToast`）。

**接入一个 Screen**：

1. `implements ErrorToastSupport` + `@Nullable private Component errorToast;`，实现 `setErrorToast`。
2. `render()` 开头：`renderBackground` → 若 `errorToast != null` 则 `ErrorToast.render(...)` 并 **`return`**（早返回，下层 UI 不渲染不交互）。
3. `keyPressed` / `mouseClicked` 里：`errorToast != null` 时 ESC / 点击清空并 `return true`（吃掉输入）。

**触发**：本地校验 `errorToast = Component.translatable("..."); NotifySound.clientError();`；服务端失败正常发 `S2C_OperationResult`（`failure(key)` 等）即可，发送统一用 `CHANNEL.send(PacketDistributor.PLAYER.with(() -> player), ...)`。**失败一律横幅、没有聊天栏 fallback**（未实现接口的界面 / 无界面时由 `ErrorToastScreen` 顶上）；**成功仍走聊天**（`displayClientMessage`），只有上传成功走横幅。

**子屏幕触发父屏幕校验**：校验失败设完 `errorToast` 后要 `Minecraft.getInstance().setScreen(this)` 切回父屏，否则父屏不在渲染栈、toast 不显示。

**哪些不用改**：`command/` 命令系统、异步放置 Handler（界面已关）、成功通知、已有 `instanceof ErrorToastSupport` 的 else 兜底。

**lang 命名**：`spatial_blueprint.gui.<screen_id>.error.<name>` / `spatial_blueprint.message.<name>`；中英各一份。

**已接入 Screen**：`CoordinateEditScreen`、`UploadBlueprintScreen`、`PointSelectionScreen`、`PlacementScreen`、`BlueprintLibraryScreen`、`EngineeringBlueprintScreen`、`SafeCoordScreen`、`VoidDimensionalScreen`、`BlockSubstitutionsScreen`、`BulkConversionScreen`、`ErrorToastScreen`、`ProjectBrowserScreen`、`ProjectBlueprintScreen`、`ProjectRangeScreen`、`SubProjectMaterialScreen`。

### C2 · NBT 预算语义与 strip 分工（原理）

三种超限，后果各不相同（最容易搞混）：

| 检测 | 超限后果 |
|---|---|
| 单体 NBT **体积** | 净化时清该方块的 NBT，保留方块，上传成功 |
| 单体 NBT **深度** | 同上 |
| NBT 体积**总量** | **拒收整个文件** |

只有总量拒收 —— 它没法靠清理单个方块解决。写测试清单、改文案、答疑时不要混。

- **捕获路径刻意没有任何体积/深度限制**：OP 强制蓝图必须能原样带走全部 NBT；次元蓝图是把结构从世界搬走。真正的攻击面是上传进来的外部文件。任何"给捕获加限制"的想法先停下（测试清单里有防回归项）。
- **两个 strip 方法的分工（别搞混）**：

| 方法 | 容器策略 | 用在 |
|---|---|---|
| `stripDangerousBlockNbt` | **无条件**倒空一切容器 | 上传净化 `stripListInPlace`、`effectiveNbtBytes` |
| `stripDangerousBlockNbtKeepContents` | 仅 `containsIllegalItemDeep` 命中才整体倒 | 次元蓝图捕获（`clearAfterCapture`） |

安全项（告示牌 clickEvent / 含命令的讲台书 / 刷怪笼 SpawnData）两者都做，共用 private 的 `applySafetyStripInPlace`。给次元蓝图捕获加容器清理 = 回归；让上传路径走 KeepContents 版本也是回归（上传的蓝图能反复放置，留容器内容就是复制机）。

- **预算测量必须在净化【之后】**：统一入口是 `BlueprintSanitizer.effectiveNbtBytes`，**扫描报告 / 总量判定 / 实际清理三处必须都走它**，否则报告和实际行为会对不上。净化顺序：清容器 → 清超大 → 清超深 → 过滤实体，不能反。
- **改 `S2C_UploadReportMessage` 前先看这条**：它有 28 个字段；decode 局部变量**不要与既有变量同名**（曾把上限叫 `nbtTotal`、撞上表示总字节数的同名变量）；构造器 / encode / decode 三处顺序必须一致，其中三个 list 读取字面完全相同、返回类型也相同 —— **错一位后面全串，编译器完全不报错**；新字段一律追加在末尾，保持这个模式。
- FORCE 模式对次元蓝图不可达（见 T6）。

### C3 · 项目蓝图 / 子工程与快捷规划模式的硬约束

- 子工程创建必须先过三道判定（✚ 点下即拦并弹横幅 + `C2S_CreateSubProjectMessage` 服务端复判）：选区不得与项目范围（作者盒）完全一致、必须落在项目范围内（作者盒或已激活时状态包的占用盒）、不得与已有子工程绝对包围盒相交 —— 开发日志 e24 / e27。
