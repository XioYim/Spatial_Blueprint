## 本轮改动（2026-08-26）

### 他人预览渲染完整结构

原来别人的预览只有一个空边框 —— `renderOtherPlayerPreviews` 里 `if (e.fullData != null)`
分支是空的（注释写着 "placeholder for future extension"）。

动手前纠正了待办里的两个前提，它们让这件事比原先描述的小不少：

| 原以为 | 实际 |
|---|---|
| 「结构数据怎么拿」是待定问题 | 拉取链路早已完整接通：`/sbp download` → `OtherPlayerDownloadScreen` → `OtherPlayerDownloadListener` → `ClientBlueprintCache` → `attachFullData()` |
| 预览移动要重传数据 | `needRebuild` 判据不含 origin —— origin 是绘制时才平移的，对方举着蓝图到处走**零开销** |

四条决定：**显式**下载（不自动拉）／上限 **3** + **128 格**距离剔除／**不跟随**本地显示设置／每帧标签**照画**。

「不跟随」的附带好处：本地改显示设置时池子里的槽位一个都不用重建，只有 `bpSlot` 失效。
标签一度打算砍，算过后收回 —— 只是 `whiteText` 子集且 `drawInBatch` 不增加 draw call，
真正该管的「远处白算」已被距离剔除覆盖。

### VBO 管线槽位化（三步）

真正的卡点不是「管线是单例的」，而是那套状态**已经被复制过一次**：
`bp*` 与 `eng*` 各 7 个静态字段 + 两个逐行雷同的 `startAsyncXxxBuild`。
再加 N 个玩家就是第三、第四套，所以必须先抽类。
（`buildChunks()` 静态无状态、不碰 GL，可被任意多槽位共用。）

| 步 | 内容 |
|---|---|
| 一 | 抽 `PreviewVboSlot`（`markDirty → startBuildIfDirty → uploadOneChunk → draw → dispose`），bp/eng 各持一个实例，**行为零变化** |
| 二 | 新增 `OtherPreviewRender` + `Map<UUID, …>` 槽位池；每帧「选人 → 淘汰 → 渲染」，线框仍对所有人画 |
| 三 | 两条常驻单线程泳道 `SELF_BUILDER` / `OTHER_BUILDER` 取代 `new Thread`，总并发 **5 → 2** |

泳道分两条而非一条：他人大结构要跑几百毫秒，同队列会卡住自己转向的响应。
`bp` 与 `eng` 共用一条是免费的 —— 渲染分派本就是互斥的 `if/else`，两者不会同帧重建。

显存兜底两处：预览开关关掉 / 缓存空掉时走 `disposeAllOtherSlots`（该分支不进渲染方法，
不兜底槽位会连显存留在池里）；世界卸载时同样清池。

### 顺带修掉

- **重建请求可能被吞**：`dirty = false` 原由调用方在外面清，而 `startAsyncBpBuild` 内部
  还有一句 `if (bpBuilding) return;` —— 该早退一旦触发，这次重建就丢了。
  现在 dirty 与启动构建在方法内一起完成。（外层 `!bpBuilding` 使其实际不可达，属结构性堵漏。）
- **排队任务白算**：任务开头加 generation 检查，排队期间玩家下线或世界切换直接跳过，
  不为没人要的结构算几百毫秒。原来无队列概念，有了队列才需要这道。

### 未做

- **自动拉取**：维持显式 download。改成「看到别人预览就自动拉」才需要认真做限流与带宽预算。
- **标签的 Component 缓存**：`getName()` 每标签每帧 new 一个 `MutableComponent`，
  可在构建 `RenderEntry` 时存好，自己的预览一并受益。

## NBT 解压配额（2026-09-01）

为防止 gzip 压缩炸弹，新增 `SafeNbtIo`，统一用 `NbtAccounter` 限制解压后的 NBT 大小：普通本地/服务端读取上限 256 MB，客户端上传服务端上限 64 MB。1.20.1 没有带配额的 `NbtIo.readCompressed` 重载，因此工具类自行建立 `GZIPInputStream` 并调用 `NbtIo.read(DataInput, NbtAccounter)`；运行时超额异常包装为 `IOException`，不改变现有调用点的错误处理。`compileJava` 通过，保留 5 个既有 `ResourceLocation(String, String)` 弃用警告；未做实机测试。


## NBT 体积预算（2026-09-01）

现有防线量的是两样东西：内容危不危险（`stripDangerousBlockNbt`、`ENTITY_WHITELIST`、
`findSignRunCommand`）和方块数多不多（`maxVolume*`、`ABSOLUTE_MAX_CAPTURE_VOLUME`）。
两把尺子都不量字节数，漏过去的典型有三类：

- 命令方块单块 `Command` 上限 32500 字符 —— 不是容器不是 item，深度 2 层，方块数 1
- 玩家头颅的 base64 皮肤各不相同、无法去重 —— 几千个装饰头颅就是几 MB，且不算危险内容
- 5000 条附魔的列表深度只有 3 层 —— `maxNbtDepth=8` 看不见它，它是宽的不是深的

共同点是**方块数很小而字节数很大**，而捕获侧的上限全是按方块数定的。

新增 `BlueprintSanitizer.estimateNbtBytes(Tag, cap)`：迭代 BFS 估算序列化字节数，
累计到 `cap` 立即短路返回。短路是必须的 —— 否则为了称一个一千万元素的列表要把它整个
走一遍，等于把攻击成本转嫁给自己。迭代而非递归的理由同 `exceedsMaxDepth`（恶意 NBT
可嵌套数千层）。字符串按每字符 2 字节估算，ASCII 高估、中文低估，只用于数量级判断，
不要拿它算精确大小。

两个配置项（新增 `nbt_budget` 段）：

| 配置 | 默认 | 超出行为 |
|---|---|---|
| `maxBlockEntityNbtBytes` | 8 KB | **降级** —— 丢掉那一个方块实体的 NBT，方块本身照常录入 |
| `maxTotalNbtBytes` | 32 MB | **硬失败** —— 中止捕获，`sendResult(false)` 走错误横幅 |

`CaptureAreaMessage` 与 `CaptureProjectionMessage` 两处捕获循环都加了 `captureLoop`
标签，用于从三重循环中止。

**称重放在净化之后而不是之前**：容器清空已经砍掉大部分体积，先称会误伤正常的满箱子。

**为什么是预算制而不是继续加类型规则**：上面三类都可以往 Sanitizer 里各加一条规则解决，
但类型规则每加一条都要求你预先知道那个类型存在。明天装一个新 mod，它的 BlockEntity 里
存了一整张配方表 —— `stripContainers` 不认识它、白名单里没有它、深度也不超，字节数一称
就露馅。这是它相对类型黑名单唯一但决定性的好处。

**踩的坑**：Bash 工具的 heredoc 会被内容里的未配对单引号（如 `entity's`）打断，报
`unexpected EOF while looking for matching`。含撇号的长文本改用 Write 写成 python
脚本再执行，不要走 heredoc。

**未做**：单体降级目前只落服务端日志，玩家看不到「这个箱子的内容没保存」。
`S2C_OperationResult` 的成功分支不拼接 detail 文本（只有失败分支拼），塞进去等于静默。
要给玩家可见的提示，需要新通道或把裁剪计数写进蓝图元数据在 GUI 显示。

`compileJava` 通过，仍为 5 个既有 `ResourceLocation` 弃用警告，未实机测试。

### 验收查出的三件事（DS 未报）

1. **缺缓冲层，已修。** 原版 `NbtIo.createDecompressorStream` 是
   `DataInputStream(FastBufferedInputStream(GZIPInputStream(input)))`，DS 的实现少了中间
   那层。`NbtIo.read` 逐字节读类型标记、名字长度和每个数值，无缓冲时每次 `read()` 都要
   穿透 GZIP 的 inflate 调用链，读大蓝图文件会明显变慢。不是正确性问题，一行补上，
   `compileJava` 重新通过。

2. **`NbtAccounter` 的两个反直觉点**（字节码确认，别照记忆写）：

## TASK-007 验收 + catch 分支补完（2026-09-03）

文本 JSON 长度闸门改 fail-closed。验收 PASS，另外补了一处 TASK 写漏的地方。

### 洞是什么

前面修 14 号 DoS 时加的长度闸门 `MAX_TEXT_JSON_LEN = 8192`，放行方向选反了：
超长串在检测侧当「无命令」、在净化侧原样返回不清 `clickEvent`。

注释给的理由是「超长串必被体积检测接住」，但**这句话的前提是
`MAX_TEXT_JSON_LEN(8192) ≤ maxBlockEntityNbtBytes`**，而后者玩家可配 512 ~ 1 MB。
默认值恰好也是 8192，两者相等、一个字符都不差地闭合 —— 纯属巧合。
服主调到 65536 之后，一条 20000 字符带 `run_command` 的告示牌 JSON：
闸门放行不检测 → 净化原样返回 → 20000 < 65536 不算超大不清 NBT → **原样入库**。
书本 `pages` 走同一个函数，同一个洞。

### 为什么 fail-closed 几乎没有代价

两个函数都有 `clickEvent` 字面量前置检查，而且**在长度闸门之前**。
所以影响面不是「所有超长文本」，而是「超长**且**含 `clickEvent` 字面量」——
正常内容（告示牌单行约 384 字符、书页约 1024）根本走不到闸门。

而且默认配置下这不只是堵洞，行为还更精准了。因为扫描四级互斥里 dangerous 排在
oversized 前面，且 `effectiveNbtBytes` 本身就跑在 `stripDangerousBlockNbt` 之后：

- 改之前：闸门放行 → 体积 20000 ≥ 8192 → 归「超大 NBT」→ **整条清 NBT**，
  同一块告示牌其余几行文字一起没
- 改之后：判危险 → 净化只清空中招的那一行 → 体积降到几十字节 → 不再算超大 →
  **方块和其他行都保留**

### 补完：catch 分支也是 fail-open，TASK 里漏写了

TASK-007 的 Forbidden 写了「不要动 `catch (Throwable)`」，本意是「收窄异常类型是独立议题」，
但没注意到 catch 分支的**返回值方向**和闸门是同一个议题 —— 执行方照做，没有错。
验收时发现它仍然是：检测侧 `return false`、净化侧 `return json`，
而且净化侧的注释还挂着那句已经作废的「随后会被 oversized 整条清 NBT」。

触发条件不是「超长」（超长的被闸门拦在前面了），而是
**长度 ≤ 8192、含 `clickEvent`、但能让裸 Gson 抛异常的串** —— 畸形 JSON 是最现实的来源。
危害取决于是否存在「`new Gson()` 解析失败、但 Minecraft 的 `Component.Serializer`
能接受」的构造：两者注册的 TypeAdapter 宽容度并不一样，判「无命令」放行等于拿这个差异赌运气。

已改成与闸门同方向：检测侧 `return true`，净化侧 `return EMPTY_SIGN_TEXT_JSON`。
`logJsonAbort` 保留，留痕不变。

**「检测判危险」和「净化真的清掉」必须成对** —— 只改一边会更糟：
报告说这块危险，文件里却原样留着，两边对不上。

### 一个细节：空行常量不能用裸空串

`EMPTY_SIGN_TEXT_JSON` 是 `{"text":""}` 而不是 `""`。告示牌 `messages` 的每一项都要能被
`Component.Serializer` 反序列化成文本组件，裸空串不是合法的文本组件 JSON，
会在客户端渲染告示牌时炸。

## 次元蓝图容器内容不再被安全线倒空（2026-09-05）

### 症状

「次元蓝图把结构搬走，箱内物品跟着走」这条 2026-09-01 定下的规则，
实际上**只对 OP 成立**。非 OP 玩家用次元蓝图搬家，箱子、桶、唱片机里的东西全没。

### 根因：两条清理线，一条放行另一条照倒

`CaptureAreaMessage` 里有两个互不相干的开关：

| 开关 | 语义 | 次元蓝图取值 |
|---|---|---|
| `stripContents` | 防复制 | `!clearAfterCapture && !FORCE` → **false**（放行） |
| `stripDangerous` | 安全净化 | SAFE 且非 OP，或 SANITIZE → **true** |

防复制线确实为次元蓝图放行了容器，但安全线走的 `stripDangerousBlockNbt`
里第一句就是 `stripAllItemContainersInPlace` —— **无条件**倒空任意键名、任意层级的容器，
再补 `remove("Items")` / `remove("RecordItem")`。于是 OP 走 `stripDangerous=false`
安然无恙，非 OP 被安全线把箱子倒得一干二净。

问题出在 `stripDangerousBlockNbt` 这个方法本身把两件事焊在了一起：
「清能执行命令的东西」（真安全）和「倒容器」（防复制）。防复制这件事该由调用方按
蓝图类型决定，不该由安全方法一并代劳。

顺带确认：FORCE 模式对次元蓝图根本不可达 —— `BlueprintReportScreen` 的两个 OP 按钮
会把 category 强制覆盖成 `create` / `reward`，所以次元蓝图只可能是 SAFE 或 SANITIZE，
指望「让玩家用 FORCE」绕过这个问题是走不通的。

### 改法

`BlueprintSanitizer` 拆成三个方法，安全项抽公共：

- `applySafetyStripInPlace(CompoundTag)`（新，private）——
  告示牌 clickEvent、含命令的讲台书、刷怪笼 `SpawnData`/`SpawnPotentials`。不碰容器。
- `stripDangerousBlockNbt` —— 无条件倒容器 + 安全项。行为与改前逐字等价，
  上传净化路径（`stripListInPlace`、`effectiveNbtBytes`）继续用它，未受影响。
- `stripDangerousBlockNbtKeepContents`（新）—— 安全项照做，容器只在
  `containsIllegalItemDeep` 命中时才整体倒空，否则原样保留。

`CaptureAreaMessage` 按 `msg.clearAfterCapture` 二选一。

### 为什么容器判定用「含非法才整体倒」而不是逐格挑

与驮兽的 `sanitizeMobInventoryInPlace` 保持同一策略。逐格删会留下「部分保留」的
中间状态，反而更难论证安全性；整袋倒掉的代价明确，玩家也看得懂。

`containsIllegalItemDeep` 自带 fail-closed：嵌套超过 `MAX_SCAN_DEPTH`(32) 层直接判危险，
所以「用超深 NBT 藏非法物品」这条路仍然是倒空，不是放行。

### 刻意没做的事

- **实体侧没动。** SANITIZE 模式下展示框 `Item` 与盔甲架 `ArmorItems`/`HandItems`
  仍被清空，而次元蓝图会把这些实体从世界移除 —— 也就是说 SANITIZE 走次元蓝图，
  盔甲架上的装备照样销毁。这属于同一类问题，但用户这次要的是「方块 NBT」，
  实体侧留待拍板。
- **路径 B（`C2S_VoidRecaptureMessage`）没动。** 它本来就 `saveWithFullMetadata()`
  原样落盘、完全不净化，NBT 层面已经满足要求。它另有两个缺口（不捕任何生物、

### H3：物理端判断换成显式的双端入口

`AbstractBlueprintItem.getBlueprintData` 与 `SpatialBlueprintItem.getBlueprintData` 里都写着

```java
if (FMLEnvironment.dist.isClient()) return ClientBlueprintCache.get(id);
return BlueprintStorage.load(id);
```

`FMLEnvironment.dist` 是**物理端**。单人和局域网主机的物理端就是 CLIENT，

| 新入口 | 读哪里 | 谁用 |
|---|---|---|
| `getBlueprintDataServer` / `getMaterialListServer` | 文件（唯一权威） | 服务端 handler（`PlaceBlueprintMessage` ×3、`C2S_MaterialDepositMessage`、`C2S_RequestMaterialSpaceMessage`） |

**为什么 tooltip 单开一个入口**：两处 `appendHoverText` 除了这一行没有任何其它客户端引用，

## 兼容 Create 超级胶水：盒型实体的捕获与放置（2026-09-09）

### 先核实收到的审计报告，四条断言两条不成立

|---|---|
| 主因：SuperGlueEntity 未被捕获 | **成立**。捕获是白名单制，逐类 `getEntitiesOfClass`：`Painting` / `ItemFrame` / `ArmorStand` / 白名单生物 / `LeashFenceKnotEntity`。胶水是 `Entity` 直接子类，任何模式都进不来 |

| 次因：底盘 glueableSide 旋转可能不同步 | **排除**。放置走标准 `state.rotate(rotation)`，方向性 BooleanProperty 由 Create 自己的 `rotate()` 负责 |

报告还漏了一件事：放置侧本来就走通用的 `EntityType.create(nbt, level)`，
**重建胶水根本不需要 Create 依赖**，它建议的 `new SuperGlueEntity(...)` 是多余的。

### SuperGlueEntity 的真实 NBT 结构（从 Create 6.0.8 jar 反编译确认）

没有凭记忆写。`javap` 反编译服务端 mods 里的 Create 6.0.8：

```
writeBoundingBox(CompoundTag, AABB):
    tag.put("From", VecHelper.writeNBT(new Vec3(aabb.minX, minY, minZ)))
    tag.put("To",   VecHelper.writeNBT(new Vec3(aabb.maxX, maxY, maxZ)))
readBoundingBox(CompoundTag):
    VecHelper.readNBT(tag.getList("From", 6))   // 6 = TAG_DOUBLE
```

即 **`From`/`To` 各是一个 3 元 double ListTag**，就是 AABB 的两个角。
纯 vanilla 结构 —— 读写它不需要认识 `SuperGlueEntity` 这个类型。
类里还有 `span(BlockPos, BlockPos)`，说明角点落在方块边界上。

### 实现：配置化的「盒型实体」，零 Create 依赖

新增 `BlueprintConfig.BOX_ENTITIES`（默认 `["create:super_glue"]`）——
**位置由 From/To 角点描述、而不是 Pos/TileXYZ 的实体**。按注册 ID 字符串匹配，
Create 不在时该配置项无害，也不会有编译期依赖。

- 捕获 `CaptureAreaMessage.captureBoxEntities`：把 From/To 转成相对 `min` 的坐标。
- 放置 `BlueprintPlacementHandler.placeBoxEntity`：变换回世界坐标，两条放置路径都接了。

### 三个必须记住的坑

**1. 角点变换公式不带 `-1`。** 方块版是 `size - 1 - z`（方块索引跑 0..size-1），
角点跑 0..size，公式是 `size - z`。照抄方块版会让整个盒子偏一格。
为此在 `BlueprintTransform` 新增 `cornerX` / `cornerZ`，与方块版并列且注释写明了区别。

手工验算过三种旋转（size=3、胶水跨两格）：角点变换后张成的 AABB
与「两个端点方块各自用方块公式变换后再张成」的结果**逐一吻合**，90°/180°/270° 全对。

**2. 旋转后必须重新规范化 min/max。** 90°/180° 会把 From 和 To 对调，
不规范化就会写出一个反向 AABB，Create 读出来是个空盒子。

**3. `Pos` 要补成盒子中心。** `Entity.load` 先读 `Pos` 再调 `readAdditionalSaveData`
读 From/To，`Pos` 留在原捕获点会让实体先落到很远的地方。
同时 `remove` 掉 TileX/Y/Z 与 Facing —— 那些是悬挂实体的字段，对盒型实体没有意义。

### 刻意的取舍

**只捕整盒都在选区内的胶水。** `getEntitiesOfClass` 是相交判定，会把跨出边界的也捞进来。
Create 自己的做法是裁剪（`collectCropped`），但「裁一半的胶水该不该粘」是个产品问题 ——
这里直接跳过，宁可不捕，不要捕一个语义不明的。

**没改 `EntityEntry` 结构，也没改序列化格式。** 胶水复用 `entities` 列表，
`serializeEntity` 会多写几个对它无意义的字段（Pos/TileX/Facing），放置时再 remove 掉。
`deserializeEntity` 用 `rawNbt.copy()` 整份保留，From/To 不会丢。

**`EntityType.create` 返回 empty 时只记 debug 不记 warn** —— 蓝图里带着胶水、

## 次元蓝图捕获的领地校验改为遵循配置（2026-09-10）

### 症状

但判定写的是 `!player.isCreative()` —— **创造模式直接跳过**。
在开放创造的服上，任何人都能拿次元蓝图把别人领地里的建筑整片搬走，

`BlueprintConfig.DENY_CREATIVE_PLACEMENT_IN_PROTECTED_AREA`

## 次元蓝图实体侧物品放行 + 全路径口径统一（2026-09-10 下午）

承接上一节。方块容器已经改成「含非法物品才倒」，但实体侧还停在旧策略，
于是同一次捕获里箱内钻石跟着走、盔甲架上的钻石套却没了。本节把实体侧对齐，
并顺手修掉一个查出来的判定口径漏洞。

### 一、SANITIZE 下实体装备是**销毁**，不是漏带

`sanitizeEntities`（= `effMode == SANITIZE`）会无条件
`remove("ArmorItems")` / `remove("HandItems")` / `remove("Item")`；
而次元蓝图的清除阶段又**无条件**移除盔甲架与展示框（那里的注释写着
「捕获阶段无条件捕获，因此这里也无条件移除」）。

两句话合起来的实际效果是：捕获的是剥光的盔甲架，删掉的是穿着装备的盔甲架，
中间那套装备凭空消失。空间蓝图不会有这个问题 —— 它不清世界，装备还在原地。
**只有「次元 + SANITIZE」这一格会销毁。**

### 二、改法：实体三分支与方块容器严格对齐

```
stripContents （非次元蓝图）              → 无条件清空，防复制
stripEntityBad（次元蓝图 + 非 OP，或 SANITIZE）→ 只在含非法物品时整体倒
两者都不是    （次元蓝图 + OP + SAFE）    → 原样保留
```

`stripEntityBad` 就是方块那边的 `stripDangerous`，取一个 final 别名给 lambda 捕获用。
展示框、盔甲架、驮兽三处现在写的是同一个条件。

驮兽那处原来判的是 `!isOp`。当前 SANITIZE 不捕生物，所以两者在可达路径上等价，
但还是一并改成 `stripEntityBad` —— 将来谁放宽了 `captureMobs` 的门槛，这条不会漏。

新增 `BlueprintSanitizer.sanitizeEntityItemsInPlace(CompoundTag)` 做通用实现
（比原 `sanitizeMobInventoryInPlace` 多一个 `Item` 键，覆盖展示框），
`sanitizeMobInventoryInPlace` 改为委托它，现有调用点语义不变。

### 三、顺带查出来的口径漏洞：展示框判定漏掉全部纯物品

`isItemFrameItemDangerous` 原实现是：

```java
Block block = BuiltInRegistries.BLOCK.get(loc);
return block != Blocks.AIR && BlueprintConfig.isExcluded(block);
```

**它把物品 id 拿去查方块表。** 刷怪蛋、命令方块矿车、调试棒、知识之书
在方块表里查出来都是 AIR，于是一律判「安全」放行。而方块容器那边走的是
`containsIllegalItemDeep` → `isIllegalItemId`，是硬编码纯物品底线 + `_spawn_egg`

同一个刷怪蛋，放箱子里被拦，挂展示框上能过。已改为先问 `isIllegalItemId`，

这是**收紧**，跟着一起变严的还有三处调用点：捕获报告的危险扫描

方向都对 —— 报告里标出来的危险项从此和实际会被清掉的东西一致。

### 四、路径 B（虚空重捕获）也接上同一套

### 一、OP 超过类型上限时「继续创建」被误锁

症状：OP 选区方块数超过该类型上限（如空间 500k）、选区里没有非法/危险方块，
检测报告标题红「危险」，`继续创建` 灰，只能走第二排 `(OP)空间/奖励`（FORCE）。
FORCE 会把类型覆盖成 create/reward，所以超类型上限的**次元 / 投影 / 工程**蓝图
OP 根本做不出来，只能缩小选区。

根因在 `BlueprintReportScreen`：构造时初值判了 `!isOp`，但 `tick()` 收到服务端扫描回包
后重算 `state` 时没判 `isOp`，`blockCount > limit` 一律打成 `DANGER`。服务端
`BlueprintValidator.validateCaptureArea` 对 OP 的上限是 1.6M 硬底线，类型上限只对非 OP
生效 —— 报告侧的类型上限对 OP 是提示性的，锁按钮属误伤。

改法：`ReportState` 加 `OVER_LIMIT`（黄），不用 boolean 旁路 —— `state` 只在初值 /
tick / 按钮 / 标题色 / 标题后缀五处用，枚举分支自然覆盖，避免「state 说危险、另一个
flag 说其实能点」两套真值。tick 判定顺序：

```
非法/危险方块 或 (超类型上限 && !isOp)  → DANGER（锁）
超类型上限（isOp）                       → OVER_LIMIT（黄「超额」，可点）
特殊实体                                  → WARN
否则                                      → SAFE
```

刻意**不**要求 `specialEntities.isEmpty()`：OP 超额 + 带装备盔甲架（大建筑很常见）
按那种写法仍会锁死，而特殊实体单独只是 WARN。超额与特殊实体同级，都是「提醒但可继续」。

不加 1.6M 硬底线判断：用户确认选区超 1.6M 在选点页就卡住进不来报告屏。

**行为扩张（用户口径：类型上限对 OP 一律提示性）**：次元蓝图首次有了 OP 超类型上限的通道，
`继续创建`（SAFE）→ 服务端对 OP 放到 1.6M → 成功 → 按次元流程清世界入袋。
`maxVolumeDimensional` 对 OP 不再是事实硬限。

实体行为**没动**：`继续创建` 仍是 SAFE 模式，OP + SAFE 下空间蓝图剥盔甲架装备/展示框物品
（防复制），次元蓝图原样保留，生物看创造/生存 —— 与 OP 未超额点同一个按钮完全一样。
想带装备的空间蓝图还是走 FORCE 按钮。

## Create 胶水兼容实机失败 → From/To 是相对 Pos 的偏移（2026-09-12）

清单第 31 项实机：放置出来的方块**完全没有胶水**。查下来是 2.6.0 那批胶水兼容
从捕获到放置一个胶水都没经手过 —— 不是散架，是根本没捕到。

### 根因

`javap` 测试服里的 `Create 6.0.8` → `SuperGlueEntity`：

```
addAdditionalSaveData:  writeBoundingBox(nbt, getBoundingBox().move(position().scale(-1)))
readAdditionalSaveData: setBoundingBox(readBoundingBox(nbt).move(position()))
resetPositionToBB:      setPosRaw(bb.center.x, bb.minY, bb.center.z)
setPos(x,y,z):          bb 平移到盒底中心 = (x,y,z)
```

也就是说 NBT 里的 `From`/`To` 是**相对实体 `Pos` 的偏移**（盒底中心为原点，
数值都在 ±几格内），不是世界坐标。2.6.0 那批把它当世界坐标：

- 捕获 `CaptureAreaMessage.captureBoxEntities`：拿 `From`/`To` 跟世界坐标的 `captureBox`
  比「整盒是否在选区内」→ 偏移量永远落不进世界坐标的选区 → `continue` → **一个都捕不到**。
  9-09 的日志写「反编译 Create 6.0.8 确认 From/To 是纯 vanilla 的 double ListTag」——
  格式确认对了，坐标系没看。
- 放置 `BlueprintPlacementHandler.placeBoxEntity`：把世界坐标写进 `From`/`To`，`Pos` 写盒中心。
  即使捕到了，Create 读盘再 `+Pos` 一次，盒子会跑到两倍远的地方。两边错得一致，
  所以单看代码对得上，一实机就露馅。

### 改法（两处，不动 `EntityEntry` 结构与序列化）

- 捕获：几何一律取 `entity.getBoundingBox()`（权威的世界 AABB），`From`/`To` 只用来确认
  「是预期格式」。蓝图内约定不变：`From`/`To` 存相对选区 `min` 的绝对角点。
- 放置：算出世界 lo/hi 后按 Create 自己的约定写回三个键 ——
  `Pos = (cx, loY, cz)`（盒底中心）、`From = lo − Pos`、`To = hi − Pos`。
  `Entity.load` 里无论 `reapplyPosition`（→ `setPos` 把默认 bb 挪到 Pos）和
  `readAdditionalSaveData`（bb = From/To + Pos）谁先谁后，结果都是同一个盒子。
- `tick()` 只在 `bb.getXsize()==0` 时自毁，不检查底下有没有方块，放置顺序无所谓。
- 手验：方块 (100,64,200)+(101,64,200)，胶水 bb [100,64,200]→[102,65,201]，选区正好这两格
  → 捕获框边界相等不被排除 → From=(0,0,0) To=(2,1,1) → 放到 (300,70,400) →
  Pos=(301,70,400.5) From=(−1,0,−0.5) To=(1,1,0.5) → 读回 [300,70,400]→[302,71,401]，
  `contains(atCenterOf)` 两个方块中心都在。

`BlueprintConfig.getBoxEntities` 的 javadoc 补了坐标系说明，防再犯。

## 次元蓝图收紧：禁净化、非法物品整单拒收、OP 不豁免（2026-09-12）

### 为什么

实机测试里一堆项目和次元蓝图撞车 —— 根因是次元蓝图有三层判定、三种口径：
平民 SAFE 拒非法方块但倒容器，OP SAFE 什么都放行原样入库，SANITIZE 跳方块倒容器。
次元蓝图的本质是「把结构从世界里搬走，材料入袋，放置时原样放回」，
蓝图里存的和世界里消失的必须是同一份东西。净化和 OP 放行都违背这一点。

用户拍板：**次元蓝图只能建安全的，任何人一样，OP 也是。** 有非法方块 / 非法物品就
不通过，让玩家自己清理干净再来。

### 改了什么

**服务端 `CaptureAreaMessage`（只动 clearAfterCapture 分支）**
- 新增 `strictDimensional = msg.clearAfterCapture`。
- `effMode != SAFE` 且次元 → 直接拒，回 `dimensional_no_sanitize`。客户端按钮已灰，
  但 `msg.mode` 是客户端发的，改包能送 SANITIZE 进来，服务端必须再拒一次。
- 非法方块预扫的条件从 `SAFE && !isOp` 改成 `SAFE && (!isOp || strictDimensional)`，
  次元蓝图 OP 也查；同一个循环里次元蓝图再查方块实体 `hasDangerousBlockNbt`
  （容器非法物品、告示牌命令、讲台书命令、刷怪笼 SpawnData），命中整单拒。
- 预扫通过后再对选区实体跑 `findEntityWithIllegalItems`（展示框 / 盔甲架 / 白名单生物），
  命中整单拒。三道预扫都在破坏权限校验和清世界**之前**，拒收不动世界。

**服务端 `C2S_VoidRecaptureMessage`（路径 B）**

  报告标危险的服务端必拒，报告没标的服务端必放，两边对不上玩家就没法自己清理。

## 领地区块红框（2026-09-12 深夜，→ 2.6.8）

用户测 36（B 创造模式储存 A 的领地被拒）时提出：预览里应该把「处在领地内的区块」用红色额外边框标出来，
玩家圈选区时就知道哪片会被拒，不用点储存才吃横幅。

### 改法（3 文件 + 版本）

- `C2S_RequestIllegalBlocksMessage.handle`：在既有的逐格循环里，对每个区块**第一格非空气方块**
  post 一次 `BlockEvent.BreakEvent(level, pos, state, player)`，被取消 → 记 `ProtectedChunk(cx, cz)`。
  口径与次元捕获的逐格 BreakEvent 完全一致（含 `denyCreativePlacementInProtectedArea` 开关：
  创造 + false → 不采样），只是从逐格降到逐区块 —— FTB Chunks 按区块划地，一格代表整个区块；
  非区块制的领地 mod 只能拿到近似结果，真正拦截仍在捕获侧逐格判。上限 `MAX_CLAIM_SAMPLES=4096`
  次采样，超出的区块不采（只是预览少几个红框）。
  副作用核实：javap FTB Chunks 2001.3.8 的 `blockBreak` 只做 `shouldPreventInteraction` → 取消/放行，
  不给玩家发消息；捕获侧本来就逐格 post 同一个事件，采样只会更少。
- `S2C_IllegalBlocksListMessage`：新 record `ProtectedChunk(int cx, int cz)`、静态 `clientProtectedChunks`、
  第七构造参数（六参委托 `List.of()`）、encode/decode 追加在盒型实体之后（varInt 数量 + 每项两个 varInt，
  负区块坐标 varInt 能正确往返）、`handle` 在 `clientReceiveTime` 之前赋值。**动 wire → bump 2.6.8。**
- `BlueprintSelectionRenderer.renderProtectedChunks`：每个区块只画它与选区相交的那段柱体
  `[max(cx*16, selMin), min(cx*16+16, selMax)) × 选区 Y`，红 `0xFF3030`、线宽 2/16（方块框的两倍）、
  `noDepth`；旧扫描残留（不在当前选区）不画。空白选区与次元「查看范围」两处都接。
