# Spatial Blueprint 最新开发日志

## /sb config 改为读写服务端配置（2026-08-24）

### 病根

配置注册的是 `ModConfig.Type.COMMON`，**服务端和客户端各有一份自己的 toml**。
而 `/sb config` 只是让客户端打开界面（`S2C_OpenConfigMessage`），界面里直接
`BlueprintConfig.XXX.get()/set()` 读写的是**客户端那份** —— 服主在服务器上敲
`/sb config` 改半天，改的其实是自己客户端的文件，服务器毫不知情；
「保存」按钮调的 `value.save()` 落的也是客户端的盘。

以前只有体积 / 槽位两组值通过 `S2C_ConfigSyncMessage` 单向下发到客户端缓存，
配置界面根本没用它。

### 改法：让界面走一趟网络

```
打开界面 → C2S_RequestConfigMessage（服务端校验 OP）
         ← S2C_ConfigValuesMessage（服务端当前值）→ 存进 ClientConfigMirror
编辑     → 只改镜像里的 pending，不碰任何 toml
点保存   → C2S_ApplyConfigMessage（只发改过的项）
         ← 服务端校验 → 落盘 → clearCache() → 回推新快照 + 重发 ConfigSync
```

**新增五个类：**

| 类 | 职责 |
|---|---|
| `config/ConfigRegistry` | 可编辑配置项的登记表，按 **toml 路径**索引（`String.join(".", value.getPath())`）—— 那是配置文件里的真实位置，不需要另维护一张对照表 |
| `client/ClientConfigMirror` | 服务端值 + 未提交编辑；断线清空 |
| `client/ConfigAccess` | 配置界面读写的唯一入口，`get/set/save/request` |
| `network/C2S_RequestConfigMessage` | 索取当前值（OP 才回） |
| `network/C2S_ApplyConfigMessage` | 提交改动 |
| `network/s2c/S2C_ConfigValuesMessage` | 下发快照 |

**只发改过的项**，不是整份快照 —— 两个 OP 同时开着配置界面时，各自只覆盖自己动过的那几行，
不会拿一份陈旧的全量值把对方的修改压回去。

### 防改包

服务端逐项校验：操作者是 OP；id 必须在登记表里；**值必须通过该项自己的 spec**。
最后这条不是形式主义 —— 写进一个超出 `defineInRange` 的值，ForgeConfigSpec 下次校验时会把
**整个配置文件重置为默认**，一个伪造的包就能抹掉服主的全部配置。
校验走 `SPEC.getValues().get(path)` 取回 `ValueSpec` 再 `test()`，
因为 `ConfigValue` 本身不暴露取值范围。

写完回推真正落盘的值：被拒的项会在界面上自己变回去，玩家看得见。

### 已接入的界面

`GeneralConfigScreen`、`AnimationConfigScreen`（含其中的布尔开关）。
两处的 `Row` / `Entry` 记录顺带从 `ConfigValue<Integer>` 收窄成 `IntValue`。

### 未接入

列表型配置仍然直接读写本地 toml：`ExcludedBlocksScreen`、`BlockListConfigScreen`、
以及材料页那三个替换表界面。它们编辑的是 `ConfigValue<List<String>>`，
需要给 `ConfigRegistry` 加一类「列表项」并扩展两个消息的编解码，是独立的一块。


## 六个修复 + 奖励蓝图（2026-08-24）

### ① 创建冷却：点一下就起算 → 成功才起算，OP 不受限

`PointSelectionScreen` 里那个 `static lastCreateClickMs` 是在 **[创建] 按钮被按下的那一刻**
写入的，而那一步只是打开「选择创建类型」界面 —— 点开看一眼再取消，照样要等 15 秒。
而且它是客户端静态字段，OP 一样被卡。

改成服务端驱动：新增 `S2C_CaptureCooldownMessage`，在捕获全部成功、蓝图落盘、物品换好之后
才发（`notifySuccess`），**OP 直接不发**。三条创建入口都接上了
（`CaptureAreaMessage` / `CaptureProjectionMessage` / `C2S_CreateEngineeringBlueprintMessage`）。
客户端侧 `ClientCaptureCooldown` 只存一个结束时刻，断线时清空。

中途取消、体积超限、槽位已满、检测被拒 —— 一律收不到这个包，也就不进冷却。

### ② 槽位显示 0

`ClientLibraryCache.countOwnSlots()` 在列表还没拉到时 **返回 0** —— 把「不知道」和
「一个都没占」混成了同一个答案。加上 `requestIfNeeded()` 只在缓存为空时才发请求，
玩家捕获之后再打开创建页，用的还是捕获前的旧列表。

- `countOwnSlots` 未就绪时改为返回 **-1**，两处调用点显示「?」并放行（服务端仍会校验）
- 新增 `ClientLibraryCache.forceRefresh()`，`CreateBlueprintScreen` **在构造器里**调它
  —— 放 `init()` 会被版本跟随反复触发，变成请求死循环

### ③ 拦截了却还是开了 UI（测试 125 / 126 / 127）

根因是同一个：这三条的共同前提都是「该蓝图数据从未下载过」，此时 `data == null`，
早期守卫全都判不了 → 界面照常打开 → 数据到达后由 `tick()` 的迟到守卫补判。
而补判用的 `ErrorToastScreen.show()`：

```java
if (mc.screen instanceof ErrorToastSupport toastScreen) {
    toastScreen.setErrorToast(message);   // ← 只在当前界面上挂一条横幅
}
```

`PlacementScreen` 实现了 `ErrorToastSupport`，所以横幅是画在**还开着的**放置界面里的，
关掉横幅又回到了本该被拦住的界面。

新增 `ErrorToastScreen.showExclusive()` —— **始终替换当前界面**。
`ForceBlueprintGuard` 的三个拦截全部改用它（拦截的含义就是「你不该待在这个界面里」）。
顺带：`SpatialBlueprintItem` 里那份内联的次元归属检查删掉，改调同一个守卫，
两边规则不会再走样；迟到守卫补上了 `data.placed` 那一条。

### ④ 上传：仅空间 tab 创造专用 + 拒绝 FORCE 蓝图

- 服务端原来对**所有**上传都要求创造模式，改为只在 `category == "create"` 时要求
- `StructureFileScanner` 增加 `isForceCaptured()`（读 `SpatialBlueprintData.saveMode`），
  FORCE 蓝图在列表里**列出但禁用**：文件名标红、按钮变成红色「禁止」、悬浮说明原因 ——
  直接隐藏的话玩家只会以为文件没放对地方
- 上传出口与服务端各拦一道（FORCE 跳过了非法方块检测与 NBT 净化，放行等于给出一条
  「本地造个 FORCE 蓝图再传上来」绕过检测的路）

### ⑤ FORCE 捕获恢复无限制

上一轮把「非次元蓝图无条件倒空容器」做成了对 OP 也生效，这次加回 FORCE 例外：
`stripContents = 非次元 && effMode != FORCE`。空间与投影两条捕获路径都改了
（投影侧连展示框物品、盔甲架装备、驮兽箱子一并跟着 `stripContents` 走）。

### ⑥ 奖励蓝图（新类型）

投影蓝图的特殊变体，OP 在检测报告第二排的 **[(OP)奖励蓝图]** 创建。

| | |
|---|---|
| 物品 | `reward_blueprint`，继承 `ProjectionBlueprintItem`，`isFoil()` 返回 true（附魔光效） |
| 分类 | `reward`，存 `config/spatial_blueprint/reward/` |
| 材料清单 | **创建时为空**，放置完全免费（FORCE 创建 → `opBypassCapture` 天然为 true） |
| 用后 | **销毁**（`ItemStack.EMPTY`），与空间蓝图一致 —— 投影可反复用，奖励要是也能反复用，发一张等于发无限张 |
| 槽位 | **不占**（`getSlotLimitFor("reward")` 恒返回 0） |
| 列表 | 只有 **OP** 在**空间蓝图 tab** 里看得到；名字金色加粗 + 后缀「(奖励)」 |

**检测报告按钮改成两排**：

```
第一排  [净化并继续]  [继续创建]  [取消创建]
第二排  [(OP)空间蓝图]  [(OP)奖励蓝图]
```

第二排两个都是 FORCE，且**覆盖上一步选的类型** —— 上一屏定的是「建哪种」，
这两个按钮自己决定建成空间还是奖励。因此 `startCapture` 多了一个带类型覆盖的重载。
启用条件是 **OP + 创造模式**（提示文案里写明了「仅限于创造模式OP玩家使用」）。

旧的 `btn.op_force` 三个语言键已删除。

## 上传格式扩展：.nbt / .schem + 目录与分页重整（2026-08-22）

依据 `蓝图待办支持上传格式分析报告.txt`，四种结构格式全部接上，
上传界面的三个 tab 改为按「文件属于哪类蓝图」分页。

### 支持的格式与来源（速查）

四种全部从 `.minecraft/schematics/` 读，只扫第一层，扩展名匹配**大小写不敏感**。

| 扩展名 | 格式 | 主要来源 | 解析器 | 实体 |
|---|---|---|---|---|
| `.litematic` | Litematica 自有格式（gzip NBT，多区域 + 变长位压缩调色板） | Litematica mod；**本 mod 导出的蓝图也是这个格式** | `LitematicaImporter` | ❌ |
| `.nbt` | 原版 `StructureTemplate`（gzip NBT，稀疏 blocks 列表） | 原版结构方块；**Create 蓝图**（Create 无自有格式） | `StructureNbtImporter` | ✅ |
| `.schem` | Sponge Schematic v1 / v2 / v3 | WorldEdit `//schem save`；各建筑站导出 | `SpongeSchematicImporter` | ❌ |
| `.schematic` | MCEdit / Schematica 老格式（`Blocks`+`Data`+`AddBlocks`，YZX） | MCEdit、Schematica mod（1.12 时代建筑站） | `SchematicImporter` | ❌ |

要点：

- **只有 `.litematic` 可能带 `SpatialBlueprintData.category`** —— 那是空间 / 投影 tab 的分类判据，
  另外三种格式的规范里没有地方放这个字段，因此恒归「其他结构文件」。
- **只有 `.nbt` 能带实体进来。** 另外三种在解析阶段就把实体丢了 —— 这正是上传检测报告
  「将被丢弃的实体」那一栏在此之前**永远是空的**的原因。导入的实体仍要过
  `ENTITY_WHITELIST`（只有 `painting` / `item_frame` / `glow_item_frame`），
  盔甲架、生物、Create 的强力胶都会被丢。
- **`.schematic` 只认 1.12 及以前**：方块用数字 ID（0–252 映射表），1.13+ 的文件方块会全变空气。
  tooltip 里已标注版本，免得玩家拿新文件来试然后以为是 bug。
- **跨版本处理一致**：认不出的方块回落成空气并计数（日志 `未识别方块=N`），
  不因为几个方块认不出来就整份拒收。
- **目录是三个 mod 共用的**：Create 服务端上传的副本在 `schematics/uploaded/<玩家名>/`，
  我们只扫第一层，天然不会误抓。


### 目录：`.minecraft/schematics/`，启动时不存在就建

新增 `util/StructureFileScanner` —— 把「目录里有什么」从各个 Importer 里收上来。
以前每个 Importer 自己 `new File(GAMEDIR, "schematics")` 再各扫一遍自己的扩展名，
每加一种格式就要在界面刷新逻辑里多拼一次列表。现在统一为
`listAll()` + `extensionOf()`，`LitematicaImporter.listLitematics()` 与
`SchematicImporter.listSchematics()` 已删除。

`ensureDir()` 在 `clientSetup` 调一次：空目录也比「没有这个文件夹」强 ——
玩家至少知道该往哪儿放文件，而不是打开上传界面看到一片空白还不知道是没文件还是路径不对。

这个目录不是我们挑的：Litematica 与 Create 都默认用它
（`CreatePaths.SCHEMATICS_DIR = GAMEDIR.resolve("schematics")`），三个 mod 共用。

### 新增两种格式

| 格式 | 解析器 | 要点 |
|---|---|---|
| `.nbt` | `StructureNbtImporter` | 原版 StructureTemplate。**Create 蓝图就是这个格式** —— 它的 `SchematicExport` 直接调 `fillFromWorld` + `NbtIo.writeCompressed`，没有任何私有字段 |
| `.schem` | `SpongeSchematicImporter` | Sponge v1/v2/v3。1.13+ 的主流分享格式（WorldEdit 导出） |

`.nbt` 比 litematic 简单：palette 与它**同构**（`Name`+`Properties`，
`NbtUtils.readBlockState` 直接可用），`blocks` 是**稀疏列表**，
不需要 `LitematicaCodec` 那套变长位解包。

`.schem` 的两处关键差异：palette 的 key 是**完整 blockstate 字符串**
（改用原版 `BlockStateParser`），`BlockData` 是 **varint 字节流**按 YZX 顺序
（另写了 20 行的 `VarIntReader`）。版本分派：v3 把一切套进 `Schematic`，
方块相关挪进 `Blocks` 子标签；v1/v2 直接在根标签下。

跨版本的旧方块名解析失败**逐条回落成空气并计数**，不因为几个方块认不出来就整份拒收 ——
Create 自己读 .nbt 也不走 DataFixer 升级链。

### .nbt 顺带把实体导入做起来了

`.nbt` 的 `entities` 是标准原版格式（`pos` + `blockPos` + 完整实体 NBT），
是四种格式里唯一能真正导入实体的。Importer 只负责搬数据，
**白名单过滤交给 `BlueprintSanitizer.filterEntitiesInPlace`** ——
否则等于开了一条绕过白名单的口子。

★ 顺带修掉一个空转：上传检测报告里「将被丢弃的实体」那一栏以前**永远是空的**，
因为两个 Importer 在解析阶段就把实体全丢了，根本没进 `BlueprintData`。现在那栏有内容了。

### 三个 tab 改为按分类分页

判据是文件顶层的 `SpatialBlueprintData.category` —— **只有本 mod 自己导出过的蓝图才有这个字段**。

| tab | 收什么 |
|---|---|
| 空间蓝图 | `category == "create"` |
| 投影蓝图 | `category == "project"` |
| **其他结构文件**（原「投影源文件」） | 只收**没有 category 字段的**文件 —— 即不属于本 mod 的结构文件 |

第三个 tab 的语义是「不是本 mod 做的」：只要带 category 字段就说明是自家导出的，一概不收。
⚠ 因此带着 dimensional / engineering / template 字段的自家文件三个 tab 都不收 ——
那几类本来也不该从 schematics 目录上传。它上传后仍存为投影模板（与改动前一致）。

分类要读文件顶层字段，而 NBT 没有部分读取只能整份解压 —— 因此：
只对 `.litematic` 做（另外三种格式的规范里没有放它的地方），
超过 16MB 的直接归「其他」，并按「路径+修改时间+大小」缓存结果，点刷新时清空。

### 列表显示完整文件名

以前显示 `stripExt(name)`。同一个建筑常常同时存在好几种格式，去掉后缀就成了
几行一模一样的名字，根本分不出该点哪个。现在显示完整文件名，搜索也按完整名匹配
（搜 `.nbt` 能筛出全部该格式）。上传时的**蓝图名仍然去后缀**。

### 失败原因不再是一句「解析失败」

新增 `StructureImportException(failKey)`，Importer 抛出具体原因，
界面直接显示：文件已不存在 / 读取失败（不是 gzip NBT 或已损坏）/
不是有效的原版结构文件 / 不是有效的 Sponge Schematic / 不支持的格式。

### 顺带修掉的一个老 bug

`uploadSchematic(idx)` 取的是 `schematicFiles.get(idx)`，而列表渲染与点击命中用的是
`filteredFiles` —— **搜索框里打了字之后，点某一行会上传另一个文件**。已改为统一走 `filteredFiles`。

### ⚠ 已知后果：空间 / 投影两个 tab 目前基本是空的

本 mod 的蓝图存在 `config/spatial_blueprint/`，**从不往 `schematics/` 写文件**。
所以 `schematics/` 里带 `category` 字段的文件只可能来自玩家手动拷贝。
按当前分类规则，这两个 tab 对绝大多数人就是空的，所有文件都会落在「其他结构文件」。

要让前两个 tab 有内容，需要再做一个「把蓝图导出到 schematics 目录」的入口 —— 尚未实现。

### 未做

`.litematic` 与 `.schematic` 两个老 Importer 仍然返回 `null` 表示失败，
落到通用的「解析失败」文案；只有两种新格式给出了具体原因。
改造它们要动既有解析路径，等这轮实测稳定后再说。


## 创造模式放置门槛归位 + 取消生存专属类型（2026-08-22）

### 创造模式该被领地拦，不该被额外方块拦

上一轮把「非 OP 创造玩家」退回走完整校验，结果矫枉过正：他被 `EXTRA_BLOCKS`
挡住了。但创造模式本来就能随手把挡路的方块拆掉，拿这条拦他毫无意义 ——
真正该拦住他的是领地插件。两条规则的分工重新理清：

| 检查 | 判据 |
|---|---|
| 额外方块 / 实体阻挡 | **游戏模式**：创造一律跳过（含非 OP） |
| 领地保护 | `denyCreativePlacementInProtectedArea`（默认 true，创造同样受约束） |

- `PlacementPreValidator`：新增 `creativeBypass = player.isCreative()`，
  实体查询与逐块 `canBeReplaced()` 判定都跳过；Y 越界与区块未加载**仍然查** ——
  那是物理上放不下，不是权限问题。
- `BlueprintPlacementHandler.precheckPlacement`：结构冲突预检原来跟着
  `denyCreativePlacementInProtectedArea` 走，属于误用 —— 那个开关管的是
  「领地保护对创造模式是否生效」，跟「路上有没有挡道的方块」是两回事。
  改为只看 `!player.isCreative()`。三处领地预检不动。
- `PlaceBlueprintMessage` 那段镜像校验本来就写的 `if (!player.isCreative())`，无需改动。

界面表现：非 OP 创造玩家看到的是**普通白色可点按钮**，既没有红字
「OP强制放置，无视任何限制」（那是 OP 专属），也不会被置灰报额外方块。
被领地拦下时由服务端回横幅说明。

### 取消「该类型仅生存模式可创建」

投影蓝图与次元蓝图原来限定生存模式（OP 豁免），限制取消：创造模式照样能创建。
体积上限与槽位上限不受影响，仍然生效。

- `CreateBlueprintScreen`：两处 `isOp || !creative` → `true`
- `addTypeButton` 的 `needsCreative` 参数删除 —— 唯一剩下的模式门槛是
  「空间 / 工程需要创造模式」，提示文案不再需要二选一
- 语言键 `spatial_blueprint.gui.create_blueprint.need_survival` 中英文均已删除

服务端本来就没有这道门槛（只在客户端界面上判），因此不涉及防改包改动。


## 捕获内容规则重整：蜜蜂保留 + 非次元蓝图无条件倒空（2026-08-22）

原实现把「防危险」和「防复制」混成了一条规则（`stripDangerous` 按捕获模式取值），
于是出现两个方向相反的错：蜂箱里的蜜蜂被当成危险内容倒掉，而 OP 捕获的驮兽箱子
反倒原样保留。现在拆成两条互不干扰的轴：

| 轴 | 判据 | 处理 |
|---|---|---|
| **防危险** | 捕获模式（SAFE 非 OP / SANITIZE 净化，FORCE 放行） | 非法物品、告示牌命令、刷怪笼 SpawnData |
| **防复制** | 蓝图类型（次元保留，其余一律清空） | 容器物品、驮兽箱子、展示框物品、盔甲架装备 |

防复制这条与捕获者是不是 OP **无关** —— 次元蓝图是把结构从世界里搬走的，箱内物品
跟着走天经地义；其余几类都能反复放置，留着箱内物品就是一台复制机。

### ① 蜂箱 / 蜂巢的蜜蜂无条件保留

`Bees` 加进 `STRIP_SKIP_KEYS`，并从 `hasDangerousBlockNbt`（原来「Bees 非空即危险」）
与 `stripDangerousBlockNbt`（原来整窝倒掉）中移除。蜜蜂是结构本身的一部分、不是可复制的物品，
捕获一片养蜂场就是想连蜜蜂一起带走。

> `Bees[].EntityData` 仍然会被 `containsIllegalItemDeep` 递归扫到 —— 正常的
> `minecraft:bee` 扫不出问题，只有手工构造出「蜜蜂身上带非法物品」的 NBT 才会触发净化。

### ② 非次元蓝图无条件清空捕获到的物品内容

新增 `BlueprintSanitizer.stripItemContents(CompoundTag)`（方块）与
`stripMobInventoryInPlace(CompoundTag)`（生物），是 `stripDangerousBlockNbt` /
`sanitizeMobInventoryInPlace` 的「不判断、直接倒」版本。

三条捕获路径全部接上：

- **`CaptureAreaMessage`** —— 新增 `stripContents = !msg.clearAfterCapture`。
  方块 NBT：`stripDangerous` 为真时沿用安全净化（已含容器清空），否则走 `stripItemContents`；
  展示框物品、盔甲架装备、驮兽箱子同样按 `stripContents` 无条件清。
- **`CaptureProjectionMessage`** —— 原来靠一张固定键名表（`ITEM_NBT_KEYS`）清，
  看不见其他 mod 的容器、套娃潜影盒与陶罐的 `item` 单数键。改走通用清理，
  顺带补上原来完全没清的驮兽箱子。固定键名表已删除。
- **`C2S_CreateEngineeringBlueprintMessage`** —— 原来**完全没有清理**，
  工程蓝图从世界扫出来的箱子内容原样进文件；已接上 `stripItemContents`。

### ③ 背箱子的驴里的刷怪蛋没被清掉

根因就是 ②：`sanitizeMobInventoryInPlace` 前面卡了 `if (!isOp)`。刷怪蛋本身是能被
`isIllegalItemId`（`_spawn_egg` 后缀）认出来的，只是 OP 捕获时那句检查根本没跑。
现在非次元蓝图一律倒空，跟 OP 与否无关。

### 未改动 / 待确认

OP 的「强制上传」（`C2S_ConfirmUploadMessage` 的 `force` 分支）仍然完整保留上传文件里的
容器内容 —— 那个按钮的语义是「绕过检测报告，后果我担」，且有 `uploadForced` 日志记录。
若要一并按「非次元蓝图无条件倒空」处理，说一声即可。


## 删除/失效路径的四个 bug + 空容器 NBT 归一化（2026-08-22）

### ① 主人删不掉自己已放置的次元蓝图

`C2S_DeleteBlueprintMessage` 开头卡了一句 `if (player == null || !player.isCreative()) return;`。
次元蓝图本来就是给生存玩家用的 —— 主人在生存模式点 ✖，服务端一声不响地把请求丢了，
客户端还乐观地刷新了列表，看起来就是「点了没反应，文件还在」。

改为：非次元蓝图沿用创造模式限制（蓝图库管理本来就是创造侧的事），
次元蓝图的删除 / 归档与游戏模式无关。

### ② 删除确认框说不清后果

原来只有一句「删除后无法恢复」，而且 `archiveMode` 的判定（`isDim && !placed`）
跟服务端的分支完全对不上 —— 未放置的次元蓝图服务端是**一律拒绝**，根本不会归档。

确认框现在按服务端的真实分支给三段信息：

1. **这次操作是什么** —— 「文件将被永久删除，无法恢复」/「文件改名为 .bak 归档，管理员可恢复」
2. **槽位** —— 「将释放 1 个次元蓝图槽位」/ 投影 / 投影模板 /「该类型不占用云空间槽位」
   （空间与工程蓝图不限槽位，删了也腾不出东西，得说清楚）
3. **连带后果**（次元蓝图专属，红字）—— 次元袋材料会被清空、对应的空置次元蓝图会失效

`isDeleteArchiveMode()` 与 `C2S_DeleteBlueprintMessage` 的分支一一对应：
`placed && !owner && op` 才是归档。面板尺寸改为由行数与最长行反推，按钮跟着面板居中。

### ③ 「重新储存」时原文件已被归档 → 报错报成「这不是你的次元蓝图」

`C2S_VoidRecaptureMessage` 里归属校验排在文件校验前面。文件被改名成 `.bak` 之后
`ownerUuidOf()` 查不到记录、返回空串，于是先撞上归属校验。

两处检查都提到了世界扫描**之前**（原来在扫完整个区域之后才判，白扫一遍），并调换顺序：
先判文件在不在，再判归属。文件没了时不再只是报错 —— 直接把这枚已经没有归宿的
空置次元蓝图换成空白蓝图，用 `error.void_blueprint_orphaned`
（「对应的蓝图文件已被删除，该空置次元蓝图已失效 / 已替换为空白蓝图」）。

### ④ 右键文件已被删除的蓝图 → 报「该蓝图的结构已被放置」

新增 `util/OrphanBlueprintGuard`：右键时**服务端**检查该物品的 `blueprintId`
在磁盘上还有没有对应文件，没有就换成空白蓝图 + 弹
`error.blueprint_file_missing`（「对应的蓝图文件已被删除或归档 / 该蓝图已失效，已替换为空白蓝图」）。

接在 `SpatialBlueprintItem`（空间 / 次元）与 `ProjectionBlueprintItem` 的
`use` / `useOn` 上，判定必须在服务端 —— 只有服务端看得到磁盘。
空置次元蓝图早就是这个模式（`handleServerUse`），这次只是补齐其余几类。

### ⑤ 材料空间「[点击删除清单]」确认弹窗改用原版按钮

原来是两个手绘矩形 + 手写命中判定。改成真正的 `Button` Widget：
弹窗打开时 `init()` 只放这两个按钮并 `return`，渲染顺序改为
「列表 → 弹窗底板 → `super.render()`」，否则底板会把按钮盖掉
（原来那个 `translate(0, 0, 300)` 也一并去掉了）。点弹窗外面仍然等于取消。

### ⑥ 空潜影盒因 NBT 写法不同存不进材料清单

同一个空潜影盒在游戏里有两种等价写法：

```
{id: "minecraft:brown_shulker_box", Count: 1b}
{id: "minecraft:brown_shulker_box", Count: 1b, tag: {BlockEntityTag: {Items: [], id: "minecraft:shulker_box"}}}
```

`MaterialKey` 只剔除配置里的顶层忽略字段，两者算出的复合键因此不同 ——
表现为「手上明明是同一个空潜影盒，就是存不进材料清单」。

`MaterialKey.normalize()` 增加递归的 `pruneNoOps()`：剔除空 Compound、空 List，
以及 `BlockEntityTag.id`（它恒等于该物品对应的方块实体类型，留着只制造假差异）。
列表元素本身也会递归，潜影盒套潜影盒同样归一。`display:{}`、`Enchantments:[]`
这类同样是「有和没有完全等价」，一并剔除。

⚠ **不向后兼容**：本次改动前存下的材料清单 / 次元袋里，带空容器 NBT 的条目记的是旧哈希键，
改动后算出来的是纯 ID 键，两者对不上。按既定方针（开发中 mod 不做旧数据兼容）不做迁移。


## 工程 / 次元蓝图绑定存档 UUID（2026-08-22）

蓝图文件存在 `config/spatial_blueprint/` 下 —— 这是所有单人存档**共用**的一个目录。
空间 / 投影 / 模板蓝图拿到哪个存档都能放，本来就该共用；但工程蓝图与次元蓝图绑定了
固定坐标与维度，在别的存档里放出来只会砸坏毫不相干的建筑，次元蓝图的材料还锁在
原存档的次元袋里根本取不出来。因此给这两类蓝图加了存档归属判定。

### 存档身份：WorldIdentity

`util/WorldIdentity.java`（SavedData，键 `sb_world_identity`）：世界数据里落一个随机 UUID，
首次访问时生成，之后永不改变。静态快照按 `MinecraftServer` 实例缓存，换存档时服务器实例
会换新，`refresh()` 据此自动失效重取（走 `ServerLifecycleHooks.getCurrentServer()`），
不需要额外的启动 / 关服钩子。

`belongsToCurrentWorld(worldUuid)` 在两种情况下返回 `true`：蓝图没记 UUID（本机制之前
创建的旧数据），以及服务器信息取不到时 —— 宁可漏判也不能凭空判定玩家的蓝图不属于本档。

### 数据链路

- `BlueprintData` 新增 `worldUuid` / `worldName`，随 `SpatialBlueprintData` 一起序列化。
- `WorldIdentity.stamp(data, level)` 在**全部**蓝图创建入口盖戳（捕获空间 / 投影、
  工程创建的两条分支、工程副本、上传确认、次元重新储存），共 7 处。所有类型都记录来源，
  但只有工程 / 次元两类会被拦。
- `BlueprintSummary` 新增 `foreignWorld`（布尔）+ `worldName`。**存的是结论不是原始 UUID** ——
  判定在 `listSummaries()` 里就地做完，因为客户端拿不到当前存档 UUID。
  记录方法 `worldLocked()` = `foreignWorld && (engineering | dimensional)`。
- `S2C_LibrarySyncMessage.writeSummary/readSummary` 跟着加两个字段（`S2C_VoidBagSyncMessage` 复用同一对编解码）。
- 新增 `S2C_WorldIdentityMessage`，登录时推给客户端，存进 `client/ClientWorldIdentity`
  （`ClientPlayerNetworkEvent.LoggingOut` 时清空）。客户端右键就能就地判断，不必等一个来回。

### 界面表现

- 蓝图列表行：备注列**强制覆盖**成红色「此蓝图不属于该存档」，压掉玩家自己写的备注。
- 悬浮 tooltip：工程 / 次元蓝图追加「所属存档：<世界名>」（外档时红色），
  外档时再加一行红色加粗的「此蓝图不属于该存档」。
- 选中外档蓝图时，**整行底部迷你按钮隐藏**（✎ ♦ ✂ ✔ ✖ ♻ 全部）。
  副作用：这类蓝图无法在列表里删除，只能靠右键手上的物品销毁 —— 按需求如此实现。

### 右键拦截

| 物品 | 拦截点 | 处理 |
|---|---|---|
| 空间 / 次元蓝图 | `SpatialBlueprintItem.openPlacementScreen` + `PlacementScreen` 迟到补判 | 横幅 + 销毁物品 |
| 工程蓝图 | `EngineeringBlueprintItem.openEngineeringScreen` + `EngineeringBlueprintScreen` 迟到补判 | 横幅 + 销毁物品 |
| 空置次元蓝图 | `VoidDimensionalBlueprintItem.handleServerUse`（本来就是服务端判定） | 直接销毁 + 结果提示 |

客户端侧统一走 `ForceBlueprintGuard.interceptForeignWorld()`：清预览状态 → 清客户端缓存 →
发 `C2S_DiscardForeignBlueprintMessage` → 弹横幅。服务端收到后**重新校验 `worldUuid`** 才销毁，
不信任客户端判断（否则伪造包能洗掉玩家正常的蓝图）。**OP 也不例外。**

只销毁玩家手上的物品，**不动磁盘上的 .dat** —— 那份文件是另一个存档的资产，删了会把
人家好端端的蓝图一起弄没。

空置次元蓝图的存档身份记在物品 NBT 上（`PlaceBlueprintMessage` 生成 BuildBlueprint 时写入
`worldUuid` / `worldName`，`BuildBlueprintItem` 还原时透传），因为它指向的是「结构放在世界里
的哪个坐标」，服务端一眼就能判。

### 防改包底线

- `PlaceBlueprintMessage`：外档的工程 / 次元蓝图一律拒绝放置。
- `C2S_VoidRecaptureMessage`：外档的空置次元蓝图拒绝「重新储存」——
  否则会把本档的方块覆盖写进另一个存档的蓝图文件里。

### 新增语言键

`gui.library.foreign_world`、`gui.library.tooltip.world`、`message.foreign_world.blocked`、
`error.foreign_world`、`error.foreign_world.discarded`（中英各一份）。

## 工程材料面板对齐投影 + 传送权限移除按钮 + 动画线序（2026-08-22）

### 工程蓝图材料清单改成投影同款

工程界面原来那套材料区是独立写的一份，跟投影的逐渐分叉：格子尺寸、可见行数、
内容宽度、图标缩放都不一样，滚动条也是另一套。现在布局常量整组对齐 `PlacementScreen`：

```
MAT_COLS=4  MAT_PANEL_W=298  MAT_PAD=8  MAT_HEADER_H=12
MAT_CELL_W=(298-16-4-2)/4    MAT_CELL_H=17  MAT_VISIBLE=6
MAT_ICON_SCR=16（与 /sb space 一致的原生尺寸，图标不缩放，只缩数量文字 0.75）
```

`matContentY` / `matPanelX..H` / `matScrollRow` / `matMaxScrollRow` 的语义也与投影一致，
命中判定（`materialStackAt`）因此可以照抄同一套算式。

> 两边现在是「同款但各写一份」。抽成公共 `MaterialPanel` 组件的方案（约 300 行重复）
> 已确认要做，但需要投影 / 次元 / 工程三条线的完整回归，排在功能收敛之后。

### /sb tpperm list 每行挂一个 [移除] 按钮

列表原来只是干念一串名字，要撤权得自己手打 `/sb tpperm revoke <名字>`。
现在每个名字后面追加红色 `[移除]`，带 `ClickEvent.RUN_COMMAND`。

按**玩家名**而不是 UUID 拼命令 —— `GameProfileArgument` 能解析离线玩家的名字，
用 UUID 反而解析不了。名字解析不出来（档案缓存里没有）的那一行不挂按钮，
免得点出一条必然失败的命令。

### 放置动画：白色内框盖住了更粗的动画线

`Outliner` 的渲染优先级**只有两档**（`< 2` 和 `>= 2`），同一档内的先后顺序取决于
HashMap 迭代顺序 —— 也就是随机的。原来白框用 `renderPriority(3)`、填充线也在高档位，
两者同档，于是白线时不时压在更粗的动画线上面。

改成白框 `renderPriority(1)`、填充线 `renderPriority(3)`，分处两档，

## LSO 环境温度来源与 Healthy Diet 接入边界（2026-08-14）

### LSO 的世界环境温度来源

LSO 的完整世界温度不是单一群系值，而是由多项修饰器组合：

| 来源 | 当前默认行为 |
|---|---|
| 维度 | 数据包定义维度基础温度和海平面 |
| 群系 | 启用；群系温度倍率 `18.0`，炎热干燥群系夜间还有额外降温 |
| 海拔 | 每离海平面 64 格变化 `-6.0℃`，线性计算 |
| 方块与流体 | 营火、岩浆、熔炉、火把、冰、LSO 加热器/冷却器等数据包热源 |
| 天气 | 雨 `-2℃`，雪 `-6℃` |
| 昼夜 | 正午升温、午夜降温，基础振幅 `2℃`；极端群系会放大 |
| 阴影/阴天 | 白天满足温度阈值时最多附加 `-6℃` |
| 地下 | 距地表 10 格开始，16 格达到最大；群系影响乘 `0.8`，并平滑昼夜与季节影响 |
| 季节 | 可接入 Ecliptic Seasons 或 Serene Seasons |
| TerraFirmaCraft | 安装后可替换 LSO 的群系、昼夜、季节和海拔来源，其余修饰器保留 |

LSO 方块温度默认最大影响距离为 20 格；室外距离乘 `0.5`，特定垂直方向距离乘 `0.75`。
`BlockModifier` 还会处理距离衰减、传播/遮挡、方块状态及冷热源聚合，具体方块数值由数据包提供。

### 只影响玩家体感的来源

以下内容会改变 LSO 的玩家目标温度，但不是一个地点本身的环境温度：

| 来源 | 当前默认值或行为 |
|---|---|
| 玩家着火 | `+12.5℃` |
| 冲刺 | `+1.5℃` |
| 湿度 | 完全湿透时最多 `-10℃` |
| 细雪冻结 | 随冻结时间增加，最多 `-10℃` |
| 玩家抱团 | 1 格内每名附近玩家 `+0.5℃`，可以叠加 |
| 装备和手持物品 | 按 LSO 物品温度数据与属性计算 |
| 护甲涂层 | 提供加热、制冷或双向温度抗性 |
| 其他 | 坐骑、食物温度效果、Origins、冷热抗性及动态修饰器 |

因此比较环境时不能把 LSO 温度计显示的玩家体感值直接当作纯环境值；玩家是否着火、冲刺、潮湿、穿戴装备等都可能改变结果。

### Healthy Diet 实际使用范围

按本次后续决策，`hd:shelf` 在 LSO温度开启且分类接口完整可用时改用 LSO全部“位置世界环境”修饰器，但仍不读取玩家体感修饰器。实现反射遍历 LSO修饰器注册表，并分成：

```text
环境 = 维度 + 群系(含地下) + 海拔 + 季节(含地下) + TFC等世界集成
方块 = 方块与流体
气象 = 昼夜(含地下) + 天气(含雨雪、阴影/阴天)
最终环境温度 = 环境 + 方块 + 气象
```

地下和阴影不是独立注册项：地下效果已揉进群系、昼夜和季节，阴影已揉进天气。调用统一传 `player=null`，因此玩家着火、湿度、冲刺、装备、手持物品、玩家抱团等 player influence 不进入食物环境。

三组采用全有或全无策略：任一 LSO分类调用失败、温度关闭或未安装 LSO时，整组回退为 HD群系分段换算 + `5x3x5` 方块扫描 + HD天气/昼夜，禁止 LSO与HD分类混搭。LSO原始值保持其约20℃舒适基准，不额外转换为 HD标尺。

### 诊断命令

新增命令：

```mcfunction
/hdtemperature
```

命令按执行玩家脚下位置立即重新采样，并输出一行可悬浮按钮：

```text
LSO 可用：[温度对比] [HD] [LSO(使用中)] [差值-2.00]
LSO 不可用：[温度对比] [HD] [LSO(不可用)]
```

`[温度对比]` 显示位置、采样方式和 `hd:shelf` 当前实际来源；`[HD]` 显示纯 HD群系、方块、气象和最终温度；`[LSO]` 显示分类后的 LSO环境、方块与流体、气象和最终环境温度；`[差值]` 显示 `LSO最终环境 - HD最终环境` 的公式和具体数值。

## JEI 集成 + 实测 bug 修复（2026-08-14）

### JEI：材料清单查配方

jar 放在 `libs/`（编译期 API）与 `run*/mods/`（运行期加载），`build.gradle` 用
`compileOnly fg.deobf(files(...))` + `flatDir` 引入。

**三层隔离**保证 JEI 不在场时不崩：

```
界面代码 → SBJeiSupport（不含任何 mezz.jei 引用，先查 ModList）
              → JeiBridge（唯一接触 JEI API 的类）
                  → SBJeiPlugin（@JeiPlugin，由 JEI 自己扫描并注入 runtime）
```

`SBJeiSupport` 里绝不能出现 JEI 类型 —— 否则 JVM 解析这个类时就
`NoClassDefFoundError`，判断「JEI 装没装」的代码自己先崩了。

按键分配（**仅生存模式**接管，创造模式的右键是编辑菜单，不能抢）：

| 界面 | 左键 | 右键 |
|---|---|---|
| PlacementScreen（生存） | JEI 来源 | JEI 用途 |
| PlacementScreen（创造 OP） | — | 编辑清单菜单（不变） |
| 工程界面（生存） | JEI 来源 | **保留原菜单** |

工程界面只接管左键 —— 那边的右键菜单没有创造模式限制，生存玩家要用它
「存入指定数量」，抢过来会弄丢功能。因此工程界面没有「用途」页。

### 材料清单删空后面板消失

`isProjection()` 一个方法承担了两种语义：「有清单」与「清单非空」。OP 删掉最后一条材料后
清单变空 → `isProjection()` 转 false → 面板不再渲染、⎙ 也没了 → **他没机会保存这份空清单**。

拆成两个：`hasMaterialList()`（面板显隐、材料按钮可点）与 `isProjection()`（材料校验、
快捷存入）。空清单现在照常显示面板与底部按钮，内容区居中显示
「该蓝图构建不需要消耗任何材料」—— OP 可以有意存一份**不消耗材料的免费蓝图**。

### 丢弃预览中的蓝图 → 别人视角的框永久卡住

清除逻辑本来就写好了（`tickPreviewBroadcast` 开头「手上没蓝图 → sendPreviewClear()」），
但那个方法被放在 `onClientTick` 里**四个提前 return 之后**，第一个就是「手上不是蓝图」。

玩家一把蓝图丢出去就直接 return 了，**那段清除代码是永远走不到的死代码**，
服务端 tracker 条目永不清除。把广播调用提到所有 return 之前即可。

### 他人预览框颜色一律是空间蓝

广播消息里根本没带蓝图类型，收到的一方只能用一个写死的浅蓝常量 —— 所以绿色的投影蓝图
在别人眼里是蓝色的。给 `C2S_PreviewUpdateMessage` → `ServerPreviewTracker` →
`S2C_PreviewBroadcastMessage` → `ClientOtherPreviewCache` 这条链补上 `category` 字段。

颜色走广播字段而不是「下载蓝图数据后读 category」—— 后者要等数据到达，中间那段时间仍是错色。

### FORCE 蓝图闪屏 + 缺音效

`tick()` 每帧都跑 `ForceBlueprintGuard.intercept()`，命中后只 `return` 不去重 ——
非 OP 持 FORCE 蓝图时**每帧**弹一次横幅 + 发一个销毁包，表现就是疯狂闪屏。
加 `lateGuardChecked` 标志只处理一次。

「缺音效」与它同源：数据未下载时右键**完全不触发拦截**（界面照常打开、无声无提示），
数据到达后才在 tick 里触发，而那时又被闪屏淹没。

### 次元蓝图归属的两个洞

服务端 `PlaceBlueprintMessage` 用的还是**旧机制** `creatorName`：

- `creatorName` 为空时**视为是主人** —— 刚捕获还没写名字的蓝图，谁捡到都能用
- **OP 直接豁免** —— 与「次元蓝图与主人的次元袋一一绑定」的前提冲突

已统一改用 `ownerUuid`，与蓝图库、右键入口的判定一致。客户端侧右键入口在
`data == null`（别人刚捡到、没下载过数据）时会放行，改为在 `tick()` 里补判归属。

### 蓝图列表崩溃（NPE）

`ClientLibraryCache.get()` 的契约是「未拉取到时返回 null」，而新加的 `countOwnSlots`
直接遍历了它 —— 蓝图列表 `init()` 一打开就调用，那一刻数据往往还没到。

顺带修了一处更隐蔽的错误：插入该方法时选错锚点，把 `get()` 的 javadoc 与 `@Nullable`
注解跟方法本体**拆散**了，`@Nullable` 落到了返回 `int` 的 `countOwnSlots` 上。
编译不报错，但契约标注完全错位。

### 其他

- 「选择创建类型」标题写死 `cy - 105`，与名称框顶部只差 4px（字高 9px）→ 改为跟随布局的 `startY - 16`
- `MaterialItemPickerScreen` 的添加/取消改为原版 Button。连带调整：对话框背景必须移到

- `CreateBlueprintScreen` 补 `requestIfNeeded()` + 版本跟随 —— 玩家没开过蓝图库时

## 上传接入检测报告（2026-08-14）

### 为什么必须在服务端扫描

非法方块/物品列表是**服务端配置**，客户端本地 toml 在多人服上可能完全不同。
客户端自己扫出「没问题」，传上去照样被拒 —— 报告反而成了误导。

因此走「先传文件 → 服务端扫描但不落盘 → 回报告 → 玩家确认 → 保存暂存的数据」。
新增 `server/PendingUploadRegistry`：按玩家 UUID 暂存，TTL 5 分钟，**取出即消费**

单类最多记 200 条（`MAX_SCAN_ENTRIES`）—— 界面显示不下更多，网络包也不该被撑爆。

| `ADMIN` | `admin_<date>.log` | 90 天 | 需要追查的事件（体积小、价值高，所以留更久） |

路径 `config/spatial_blueprint/logs/`，与蓝图存档同级。按日期滚动，启动时按各自的保留天数清理超期文件（配置 0 = 永久保留）。

多行格式，与方案书第 7 节一致：

```
[2026-08-14 15:44:02] PLACE | Player: Steve (uuid) | Blueprint: "古城" (8f3a-...)
  Dimension: minecraft:overworld | Origin: (128,64,-300) | End: (145,80,-280)
  Blocks: 1842 | Mode: SAFE | Category: project
```

起点/终点都记：终点按**旋转后**的实际包围盒算（90°/270° 时 X/Z 互换），不是直接加 size。

### 管理员通道记了七类事件

| 事件 | 触发点 |
|---|---|
| `FORCE_PLACE` | 强制捕获蓝图的放置 —— 内容从未净化 |
| `ARCHIVE_DIMENSIONAL` | OP 归档次元蓝图（含蓝图主人信息） |
| `DISCARD_ORPHAN_BAG` | 玩家丢弃孤儿次元袋 —— 材料永久消失，申诉时要凭据 |
| `ORPHAN_BAGS_DETECTED` | 玩家上线发现孤儿袋 —— 让 OP 看到自己的清理影响了谁 |
| `FORCE_BLUEPRINT_DESTROYED` | 非 OP 手持 FORCE 蓝图被销毁 |
| `UPLOAD_REJECTED` | 上传被拒（含非法方块）—— 反复被拒说明有人在试探 |
| `UPLOAD_APPROVED` | **预留**，等审核队列落地后接入 |

原先散落在各处的 `LOGGER.info("[ARCHIVE]...")` / `[ORPHAN]` / `[op_bypass]` 全部改走这条通道。

### 一个差点写错的顺序问题

放置日志最初写在 `data.opBypassCapture` 判断那里（原 `[op_bypass]` 日志的位置），
但那个位置在**领地插件预检（`precheckPlacement`）与材料扣除之前** ——
被领地拦下或材料不足而中止的放置也会被记成一次成功放置。

已移到 `startPlacement()` 调用之前、所有 `return` 路径之后。

### 写入策略

**同步写 + 每条 flush**。放置蓝图不是每 tick 的高频事件，这点 IO 换的是服务器崩溃时日志不丢。
writer 按通道各持一个，跨天自动换文件；`ServerStoppingEvent` 里关闭句柄。

IO 异常只警告不抛出 —— 日志写不下去不该影响玩家的正常操作。

## 非法物品深度检测 + 生物容器净化（2026-08-14）

### 为什么原来的检测漏得厉害

三个洞：

1. **只有「非法方块」列表，没有「非法物品」列表**。`isItemFrameItemDangerous` 那句
   `BuiltInRegistries.BLOCK.get(loc)` 对**纯物品**返回 AIR —— 刷怪蛋、命令方块矿车、
   debug_stick 这类东西根本不在方块注册表里，一律判为安全。
2. **容器只认原版的 `Items` 键**。其他 mod 用 `inventory` / `contents` / 自定义键的容器
   完全看不见，内容原样进蓝图。陶罐的 `item`（单数，1.20.2+）同理。
3. **蜂箱 `Bees` 无人管**。`Bees[].EntityData` 是完整实体 NBT，和刷怪笼的 `SpawnData`
   是同一条绕过「禁止生物」的路，但代码里只堵了后者。

### 按 `id` 键递归扫，而不是扫所有字符串

新增 `containsIllegalItemDeep(Tag)`：BFS 遍历 NBT 树，**只取键名为 `id` 的字符串值**去判定。

不扫所有字符串是因为误报会高到不可用 —— 告示牌上写一行 `minecraft:barrier`、
玩家把物品重命名成 ID 的样子，全都会被判非法。而 `id` 是 MC 序列化 ItemStack / Entity
的固定约定（`{id:"modid:xxx", Count:1b, tag:{...}}`），**任何 mod 只要走标准
`ItemStack.save()` 就有这个键**，外层容器叫什么都无所谓。

于是一次性覆盖：套娃潜影盒、其他 mod 容器、陶罐 `item`、蜂箱 `Bees[].EntityData`、
刷怪笼 `SpawnData`。

用迭代 BFS 而非递归（恶意 NBT 可嵌套数千层，递归会 StackOverflow），
深度上限 32 层，超了直接判危险。

### 新增非法物品判定

`isIllegalItemId(String)` 取三者并集：

- `HARDCODED_ILLEGAL_ITEMS`（纯物品底线：command_block_minecart / debug_stick /
  knowledge_book / spawner）
- 新配置 `excludedItems`
- **同名方块被禁则物品形式同样禁** —— 禁止捕获基岩，自然也不该允许把基岩塞箱子里带走

刷怪蛋按 `_spawn_egg` 后缀统一拦：原版 60 多种，逐个列既啰嗦又易漏，
其他 mod 的刷怪蛋也是这个后缀。

### 净化：任意键名容器整体清空

`stripAllItemContainersInPlace` 递归识别「含字符串 `id` + `Count` 的 CompoundTag」为物品条目，
命中就删掉承载它的那个键 —— `Items` / `inventory` / `item` / `Bees` 一视同仁。

保持**整体清空**策略，不做精确删除：容器里混有非法物品就整袋倒掉。
精确删除会留下「部分保留」的中间状态，反而更难判断安全性。

⚠ **`Book` 键要跳过**。讲台的书本身就是 `{id,Count,tag}` 结构，会被通用规则当成物品整本删掉，
但原有策略是**只在书里含命令点击事件时才移除**，普通书要保留。加了 `STRIP_SKIP_KEYS`。

### 检测与净化走的是两条路（排查时别搞混）

| 入口 | 用什么 | 行为 |
|---|---|---|
| 捕获（`CaptureAreaMessage`） | `stripDangerous` 布尔 | 非 OP / SANITIZE **无条件**清空，不做检测 |
| 上传（`stripContainerAndSignNbtInPlace`） | 同上 | 无条件清空 |
| **检测报告**（`C2S_RequestIllegalBlocksMessage`） | `hasDangerousBlockNbt` | 按内容判定 |

所以把 `hasDangerousBlockNbt` 从「`Items` 非空即危险」改成「含非法 `id` 即危险」
**只影响检测报告**，捕获行为不变（仍是无条件清空，只是现在覆盖了 mod 容器）。
对报告而言这是降噪：普通箱子里放几块石头不再被列为危险。

### 驮兽箱子

驴 / 骡 / 羊驼在 `ALLOWED_MOB_ENTITIES` 里，能背箱子、穿装备、装鞍、铺地毯，
而捕获生物那段**一个净化分支都没有**（盔甲架有，生物没有）。空间蓝图可以反复放置，
于是每放一次就复制出一份箱内物品。

新增 `sanitizeMobInventoryInPlace`：非 OP 捕获时若 `containsIllegalItemDeep` 命中，
清空 `Items`/`ArmorItems`/`HandItems`/`SaddleItem`/`DecorItem` 等。
OP 的 FORCE 捕获保留原样（与盔甲架同款处理）。

`C2S_VoidRecaptureMessage` 不捕获生物（只有画/展示框/盔甲架），无需改动。

### 强制放置判定收紧为 OP + 创造

`PlacementPreValidator.validate` 原先只查 `isCreative()`，于是非 OP 的创造模式玩家
也会看到「OP强制放置，无视任何限制」的红字、按钮也是亮的 —— 但他实际会被领地插件
在服务端拦下，界面上毫无预兆。改为 `isCreative() && hasPermissions(2)`。

**这是行为变更**：非 OP 创造玩家现在退回走完整校验（EXTRA_BLOCKS / 实体阻挡等），
放不下时按钮直接置灰并说明原因。

## 次元蓝图归属制度（2026-08-13）

### ownerUuid：归属必须靠 UUID，不能靠名字

`BlueprintData` 原先只有 `creatorName`（玩家名），而次元袋是按玩家 **UUID** 分表的。
按名字判归属，玩家一改名就拿不回自己的蓝图。新增 `ownerUuid` 字段并随序列化落盘，
`isOwnedBy(UUID)` 是唯一的判定入口。

**旧蓝图（没有该字段）一律视为无主** —— 谁都不能用，只能由 OP 归档。
认错主人会让材料空间与蓝图归属彻底错乱，宁可让旧测试蓝图作废。

所有创建路径都写入了 ownerUuid（捕获、投影捕获、重新储存、工程蓝图两处、模板上传）；
`BlueprintPlacementHandler` 复制字段时也带上。两个外部导入器（Litematica / Schematic）
只有玩家名参数、且导入的不是次元蓝图，**未改**。

`BlueprintSummary` record 与 `S2C_LibrarySyncMessage` 的 `writeSummary/readSummary`
同步扩展 —— 客户端界面要靠它判断该不该显示按钮。

### 权限矩阵重排

| 状态 | 主人 | OP（非主人） | 其他玩家 |
|---|---|---|---|
| 未放置 | **不可删** | **不可归档** | 不可 |
| 已放置 | 真正删除 | 归档 `.bak` + 写日志 | 拒绝 |

未放置的次元蓝图任何人都动不了 —— 材料还锁在主人的次元袋里，文件一没结构与材料一起蒸发。
真要清理只能停服后手动进服务器目录（提示文案里已写明）。

列表里选中未放置的次元蓝图时，✖ 变成**红色不可点击**按钮。实现上不需要自定义 widget：
MC 在 `active=false` 时只是把默认文字色刷成灰，`Component` 自带的 style 优先级更高，
所以 `Component.literal("✖").withStyle(RED)` + `active=false` 就能画出红色的死按钮。

### 归属校验（四道）

1. **右键次元蓝图** —— `SpatialBlueprintItem.openPlacementScreen` 拦截，只提示不销毁物品
2. **蓝图列表 ✔ 应用** —— 非主人时按钮**根本不出现**（不是置灰）
3. **`C2S_ApplyBlueprintMessage`** —— 服务端拒绝，且必须拦在工程蓝图复制分支之前，
   否则可经那条路把别人的次元蓝图复制成 engineering 文件绕过
4. **空置次元蓝图** —— 右键与 `C2S_VoidRecaptureMessage` 两处都校验。
   这条是自己补的：空置蓝图会**覆盖写回原文件**，别人拿到就等于能篡改他人蓝图

判归属用新增的 `BlueprintStorage.ownerUuidOf()`，走摘要缓存，不做完整反序列化。

### 「重新储存」不再偷偷新建

## 专用服务端启动失败：dist 隔离规则（2026-08-13）

**本 mod 此前从未在专用服务端上启动成功过**，一直只在单人测试，所以这类问题积累到今天才暴露。

### 症状与真因

客户端连 `localhost` 报 `Permission denied: getsockopt` —— 看起来像网络/防火墙问题，
实际是**服务端根本没启动**，25565 没有任何进程监听。真正的错误在 `run-server/logs/latest.log`：

```
Attempted to load class net/minecraft/client/gui/screens/Screen for invalid dist DEDICATED_SERVER
```

Forge 的 `RuntimeDistCleaner` 拒绝在专用服务端加载客户端类，mod 构造失败 → 服务端启动中止。

### 核心规则（写代码时记住这条）

| 手段 | 生效阶段 | 能否阻止服务端加载客户端类 |
|---|---|---|
| `@OnlyIn(Dist.CLIENT)` | 类加载期（Forge 剥离成员） | ✅ 能 |
| `DistExecutor.unsafeRunWhenOn` | 类加载期（引用包在 Supplier 里延迟） | ✅ 能 |
| `if (FMLEnvironment.dist == Dist.CLIENT)` | **执行期** | ❌ **不能** |

**最隐蔽的一条：lambda 会把它用到的类型带进所在类的 synthetic 方法签名。**
JVM 加载该类、构建方法表时就要解析这些类型 —— 代码根本没执行就崩了。

### 本次修掉的三处

**1. `SpatialBlueprintMod.clientSetup()`（历史遗留，主犯）**

```java
(mc, parent) -> new SpatialBlueprintConfigScreen(parent)
```
这个注册配置界面的 lambda 编译成主 mod 类的 synthetic 方法，签名里直接带 `Screen`。
服务端**还没执行到构造函数**、仅仅加载主类就崩。

修法：整块客户端初始化搬进新类 `client/ClientModSetup`（标 `@OnlyIn(Dist.CLIENT)`），
主类只留一行 `DistExecutor.unsafeRunWhenOn(Dist.CLIENT, () -> () -> ClientModSetup.init(event))`，
签名中不含任何客户端类型。

**2. `S2C_OpenConfigMessage.handle()`（历史遗留）**

lambda 体里读 `mc.screen`（字段类型是 `Screen`）并构造 `SpatialBlueprintConfigScreen`。
注册消息（`BlueprintNetwork.register()`）创建 `::handle` 方法引用时触发 `BootstrapMethodError`。

同类问题还有 `S2C_OperationResult`、`S2C_PlacementProgressMessage`。

**3. `SpatialBlueprintMod.onPlayerLogout()`（本轮新引入）**

我写成了 `if (FMLEnvironment.dist == Dist.CLIENT) ClientMaterialSpaceCache.clear();` ——
运行时判断拦不住类加载。改用 `DistExecutor.unsafeRunWhenOn`。

### S2C 消息类的标准写法

项目里大多数 S2C 消息已经是这个模式，照抄即可：

```java
public static void handle(MyMsg msg, Supplier<NetworkEvent.Context> ctx) {
    ctx.get().enqueueWork(() -> handleClient(msg));   // lambda 体只调用下面这个方法
    ctx.get().setPacketHandled(true);
}

@OnlyIn(Dist.CLIENT)                                  // 服务端会把整个方法剥离
private static void handleClient(MyMsg msg) {
    Minecraft mc = Minecraft.getInstance();
    mc.setScreen(new SomeScreen());                   // 客户端类型只出现在这里
}
```

要点：**lambda 体内不能出现任何客户端类型**（包括读 `mc.screen` 这种字段访问），
只能调用一个带 `@OnlyIn` 的方法。

### ⚠ 连接地址必须填 127.0.0.1，不能填 localhost

实测结论：

```
IPv4  127.0.0.1:25565  →  可连 ✅
IPv6  ::1:25565        →  不可连 ❌
Windows 上 localhost 解析顺序：先 ::1，再 127.0.0.1
```

服务端监听的是 `::`（IPv6 通配）但该 socket 未开双栈，实际只接受 IPv4。
客户端填 `localhost` 会先打在 `::1` 上失败，报出极具误导性的错误：

```
Permission denied: getsockopt
```

**这条错误看起来像防火墙/权限问题，实际与权限无关。** 排查顺序应该是：

1. 先确认服务端是否真的起来了 —— `Get-NetTCPConnection -LocalPort 25565`，
   以及 `run-server/logs/latest.log` 里有没有 `Done (x.xxx s)! For help, type "help"`
2. 服务端没起来 → 看日志找真正的崩溃原因（本次就是 dist 隔离问题）
3. 服务端起来了 → 换用 `127.0.0.1` 连

要让 `localhost` 也能用，得注释掉 `C:\Windows\System32\drivers\etc\hosts` 里的 `::1 localhost`，
属于改系统配置，不建议为开发方便动它。

### 离线 UUID 与 OP

`online-mode=false` 时玩家 UUID 由用户名算出（等价于 Java 的
`UUID.nameUUIDFromBytes("OfflinePlayer:<name>")`，MD5/v3）：

| 用户名 | 离线 UUID |
|---|---|
| `Dev`（runClient 默认） | `380df991-f603-344c-a090-369bad2a924a` |
| `TestPlayer2`（runClient2） | `67f79ba5-83e4-3e4c-bd13-65aae9e91ed3` |

**改用户名就等于换玩家**，材料空间（按 UUID 分表）也会跟着换一份，
`ops.json` 里的条目同时失效。

## 次元蓝图材料校验四处严重缺陷修复（2026-08-13）

实测报出四个问题，其中两个是刷物品级别的。

### 1. 次元蓝图永远免费放置（最严重）

根因：`DimensionalBlueprintItem` **继承自** `SpatialBlueprintItem`，而
`PlacementScreen.isSpatialOnly()` 用的是 `instanceof SpatialBlueprintItem` ——
次元蓝图被判定成空间蓝图，走了「材料清单仅供查阅、不校验不拦截」那条路：

- 材料清单只显示总量，不显示「已存入/需要」
- 材料不足的禁用按钮不出现
- `deploy()` 的材料拦截被跳过

服务端那侧同样形同虚设：`bagConsume()` 无袋时静默放行（本意是给 FORCE 捕获开口子），
于是没有袋子也照样放置成功。

修复：
- `isSpatialOnly()` 显式排除 `DimensionalBlueprintItem`
- 服务端改为**严格校验**：非 FORCE 捕获的次元蓝图必须持有对应次元袋，
  `bagConsume` 失败即拒绝放置并提示材料不足
- 次元蓝图的「已存入」数量改从**次元袋**读取而非普通池
  （`S2C_MaterialSpaceSyncMessage.sendFor` 新增 `voidBagId` 参数）——
  否则界面永远显示 0/N

连带调整：**创造模式捕获恢复入袋**。上一轮为避免袋子堆积改成了不入袋，
但放置校验变严格后，创造捕获的蓝图切到生存就永远放不出来（材料无从补齐）。
袋子堆积可由 OP 清理，代价远小于蓝图作废。

### 2. 已放置的次元蓝图仍可从列表取出 → 刷物品

服务端 `C2S_ApplyBlueprintMessage` 的 `placed` 拦截是在的，但**放置后没有把新的
蓝图列表推给客户端** —— 客户端 `ClientLibraryCache` 还是旧数据，
列表里那条仍显示「未放置」、✔ 按钮不置灰。

修复：`PlaceBlueprintMessage` 打完 `setPlaced` 标记后立刻推送 `S2C_LibrarySyncMessage`。

### 3. 失效的空置次元蓝图界面拦不住

原写法是客户端 `use()` 自己 `openScreen()`、服务端并行判定失效 ——
界面已经开出来了，提示横幅只是盖在上面，关掉横幅就露出本该被拦截的界面。

修复：右键改为**服务端权威**。客户端不再自行开界面；服务端校验文件存在后
发新增的 `S2C_OpenVoidScreenMessage` 才打开，失效则直接换空白蓝图 + 提示。

### 4. 刚创建的次元蓝图看不到材料清单

`PlacementScreen` 打开时 `data` 来自客户端缓存，而捕获后服务端从未推送过蓝图数据，
`data == null` → `matBtn.active = isProjection()` 为 false → 材料按钮灰着，
看起来就是「没有材料清单」。异步拉取到数据后 `init()` 早已跑完，按钮状态不会更新。

修复：
- `CaptureAreaMessage` 捕获后主动推送 `S2C_BlueprintDataMessage`
- `refreshDataFromCache()` 在 data 由 null 变为非 null 时调用 `rebuildWidgets()`
  重建控件（`PlacementScreen` 与 `EngineeringBlueprintScreen` 两处）

- **`C2S_ApplyBlueprintMessage` 仍在写废弃的 `depositedMaterials`**：材料空间重构后该字段
  已无任何读取方，属死代码。次元袋按蓝图 ID 绑定，重新应用时 ID 不变、袋子自然还在，无需恢复。

## block_substitutions.toml 每次重启被覆盖修复（2026-08-12）

### 问题描述

每次重启后，`block_substitutions.toml` 中用户修改的 `blockSubstitutions`、`generatedSubstitutions`、`bulkMaterialConversions` 三个字段全部被重置为默认值。

### 根本原因

`GeneratedSubstitutionsConfig.java` 的三个 `define()` 调用均使用 `List.of(...)` 作为默认值：

```java
.define("blockSubstitutions", BlueprintConfig.DEFAULT_BLOCK_SUBSTITUTIONS)  // List.of(...)
.define("generatedSubstitutions", List.of())
.define("bulkMaterialConversions", List.of("minecraft:water=..."))
```

Forge 的 `define(path, defaultValue)` 自动生成验证器：

```java
o -> defaultValue.getClass().isAssignableFrom(o.getClass())
```

`List.of()` 的运行时类型是 JDK 内部的 `ImmutableCollections$ListN`（或 `$List0`），而 NightConfig（Forge 使用的 TOML 库）解析 TOML 数组时返回 `ArrayList`。

`ImmutableCollections$ListN.isAssignableFrom(ArrayList)` = **false** → 验证失败 → Forge 的 `setConfig()` 调用 `correct()` 将三个字段全部重置为默认值 → `FileConfig.save()` 覆盖整个文件 → 用户修改丢失。每次启动都触发此流程。

### 修复

在 `GeneratedSubstitutionsConfig.java` 中，将三处 `define()` 的默认值由不可变的 `List.of(...)` 改为可变的 `new ArrayList<>(...)`：

```java
.define("blockSubstitutions",
    (List<String>) new ArrayList<>(BlueprintConfig.DEFAULT_BLOCK_SUBSTITUTIONS))
.define("generatedSubstitutions",
    (List<String>) new ArrayList<String>())
.define("bulkMaterialConversions",
    (List<String>) new ArrayList<>(List.of("minecraft:water=...", "minecraft:lava=...")))
```

`ArrayList.isAssignableFrom(ArrayList)` = **true** → 验证通过 → 用户修改得以保留。

### 受影响文件

| 文件 | 修改内容 |
|---|---|
| `GeneratedSubstitutionsConfig.java` | 三处 `define()` 默认值改为 `new ArrayList<>(...)`，新增 `import java.util.ArrayList` |

## 拴绳结处理简化（2026-08-12）

### 背景

拴绳结（`LeashFenceKnotEntity`）继承自 `HangingEntity`，但其 `addAdditionalSaveData` / `readAdditionalSaveData` 均为空方法，导致：

- NBT 中不写入 `TileX/Y/Z`（始终读回 0）
- 通过 `EntityType.create(nbt, level)` 路径恢复时 `this.pos` 无法还原
- 100 tick 后 `survives()` 失败，实体被丢弃并掉落拴绳物品

## 材料清单附魔 NBT 修复（2026-08-11）

### 问题描述

材料清单统计盔甲架装备（ArmorItems/HandItems）和展示框物品（Item）时，`mergeItemCount` 只从 item CompoundTag 中读取 `id` 和 `Count` 两个字段，附魔等 per-instance `tag` 数据被丢弃。导致：

1. GUI 材料面板（`PlacementScreen`、`EngineeringBlueprintScreen`）渲染物品图标时无附魔光效
2. 悬浮 tooltip 只显示 `Component.literal(entryName)`（物品注册 ID 的 lang 名），无附魔列表、耐久度等完整信息，无法判断物品状态

### 修复：新增 `itemNbtSamples` 字段

在 `MaterialList` 新增：

```java
public final LinkedHashMap<String, CompoundTag> itemNbtSamples = new LinkedHashMap<>();
```

**填充时机**：`mergeItemCount` 读取 item CompoundTag 时，若存在 `tag`（`TagType 10`）且该 ID 尚未记录，则保存首次出现的 item tag 样本。同 ID 不同附魔只保留首次见到的样本（匹配计数逻辑）。

**`getDisplayStack(String id)` 新方法**：先查 ITEM 注册表，无则查 BLOCK 转物品；构建 ItemStack 后若 `itemNbtSamples` 有对应 tag 则调用 `setTag()` 写入，返回带完整 NBT 的 ItemStack。物品/方块均不存在时返回 `ItemStack.EMPTY`。

### GUI 改动：原版完整 tooltip

**`PlacementScreen.renderMaterialPanel()`** 和 **`EngineeringBlueprintScreen`** 材料区渲染循环均做相同修改：

| 位置 | 修改前 | 修改后 |
|---|---|---|
| 图标渲染 | `new ItemStack(displayItem)` | `ml.getDisplayStack(entry.getKey())`（含 NBT，附魔光效正确） |
| hover 判断 | `String hoveredName` | `ItemStack hoveredStack` |
| tooltip | `renderTooltip(font, Component.literal(name), ...)` | `renderTooltip(font, hoveredStack, ...)` |

原版 `renderTooltip(Font, ItemStack, x, y)` 会自动生成含附魔列表、耐久度、自定义名等的完整 tooltip，与背包物品 hover 行为一致。

### 序列化持久化

`MaterialList.serialize()` 将 `itemNbtSamples` 写入 `itemNbtSamples` ListTag（每项含 `id` + `tag`）；
`deserialize()` 对应读取，旧格式蓝图（无此字段）安全忽略，不影响升级兼容性。

| 文件 | 修改内容 |

## GUI 物品渲染防崩溃（2026-08-11）

### 问题根源

模组物品若实现了 `BlockEntityWithoutLevelRenderer`（BEWLR）但存在 Bug，调用 `GuiGraphics.renderItem()` 会每帧抛出 `ReportedException: Rendering item`，导致：

- 该物品所在格永远空白（无图标）
- 每次异常耗时约 65ms，多个破损物品叠加可达 200~300ms/帧，界面明显卡顿
- BEWLR 崩溃前可能已向 `MultiBufferSource` 写入残余顶点，若不手动 `endBatch()`，这批错误数据会被下一次正常渲染的 `endBatch()` 一并提交，产生画面错误

**诊断过程**：通过 `RenderSystem.getModelViewStack()` 反射读取 PoseStack 深度，以及在渲染前后打 `[DBG-START]`/`[DBG-END]` 日志，确认 Forge 47.x 已在 `renderGuiItem()` 内用 try-finally 保证 popPose 不泄漏，MV 栈不是问题所在；真正的瓶颈是破损 BEWLR 每帧重复抛异常。

### 修复方案：已知崩溃物品缓存

```
static Set<String> KNOWN_CRASH  （静态，跨帧持久）
```

**流程**：
1. 渲染前检查 `KNOWN_CRASH`：命中 → 直接渲染 BARRIER 占位，立即返回（耗时 <1ms）
2. 正常调用 `g.renderItem()`，捕获 `Throwable`：
   - 将物品注册 ID 加入 `KNOWN_CRASH`（后续帧不再重试）
   - 调用 `Minecraft.getInstance().renderBuffers().bufferSource().endBatch()`，清空 BEWLR 写入的残余顶点
3. 崩溃后 MV 栈修复：用反射精确比较 depthBefore/depthAfter，多余 push 则弹回（Forge 47.x 实测深度稳定，此逻辑作为兜底保留）

**效果**：破损物品仅首帧崩溃一次，此后全部显示为 BARRIER 图标，渲染帧率恢复正常。

### 受影响文件

| 文件 | 修改位置 |
|---|---|
| `gui/ReferenceSubstitutionsScreen.java` | `renderIcon()` + 新增静态 `KNOWN_CRASH` 字段 |
| `gui/BlueprintReportScreen.java` | 新增 `renderItemSafe()` + 静态 `KNOWN_CRASH`，替换 `drawBlockCell` / `renderSpecialGrid` 两处裸 `renderItem` 调用 |

### 9. 预览渲染改进

- **容器方块修复**：箱子/熔炉/潜影盒等不再以文本标签显示——改为**1px 灰色线框 + 方块 lang 文本**（容器/告示牌/`ENTITYBLOCK_ANIMATED` 方块统一处理）
- **流体渲染**：水/岩浆最终用**原版静态贴图**（`block/water_still` / `block/lava_still` 图集帧，不透明，无流动动画），`emitTexturedCube` 随 VBO 上传

  **报错经历与解决办法**：
  1. 最初用原版 `LiquidBlockRenderer`（真实流体模型/流动纹理）→ 用户反馈显示有问题 → 改回纯色。
  2. 第一次手写纯色 quad 用 `uv(0,0)` → **完全不显示水**。
     - 诊断：新增日志发现流体**全部正确识别并写入 VBO**（水蓝图 2084/2084 进列表并绘制），但不可见 → 问题在渲染不在识别。
     - 根因：`rendertype_translucent` 着色器输出 = `顶点色 alpha × 纹理采样色 alpha`，`uv(0,0)` 采样到方块图集左上角**透明像素** → alpha×0 = 全透明。
  3. 中途改**蓝/橙染色玻璃模型**渲染（`Blocks.BLUE/ORANGE_STAINED_GLASS`，与放置动画一致）→ 可见但颜色固定、不随配置。
  4. **最终修复**：用项目已有的 `emitColoredCube`，UV 采样**白色方块 sprite 中心**（`block/white_concrete` 的 `cachedWhiteU/V`，`ensureWhiteSprite`）→ 采样白色不透明像素，顶点色直接可见 → 配置色半透明纯色块正常显示。

  **注意事项**：
  - BLOCK 顶点格式**含 color 顶点**，但 translucent shader 会乘纹理采样色：采样点必须是**白色不透明像素**（如 white_concrete 中心），不能 `uv(0,0)`。
  - 手写 BLOCK 顶点：1.20.1 无 `uv3()`，lightmap 用 `.uv2(light)`、overlay 用 `.overlayCoords(int)`，且每顶点必须 `.endVertex()`。
  - 诊断日志初期被 `isDebugSession()`（需创造 + `DeBug` tag）门控 → 看不到 → 调试阶段临时改 `LOGGER.warn` **无条件输出**。
  - `buildChunks` 在后台线程：只做纯 CPU 写 BufferBuilder（`emitColoredCube` 安全），不能碰 GL。
- **实体预览**：盔甲架/生物等实体在预览位置显示**黄色 1px 线框 + 实体 lang 文本**
- **未知方块**：报告方块格无物品图标且无 lang key → 显示红色斜体"未知方块"文本（不显示屏障图标）
