## 一、本机环境

### 改 UTF-8 文本不要用 PowerShell

**禁止**用 `Set-Content` / `Add-Content` / `(Get-Content -Raw) -replace ... | Set-Content` 处理 lang / json / md / py 等 UTF-8 文本 —— 会破坏编码。

### ⚠ 本机 python 是个不可用的存根，用 node 代替（2026-09-09 核实）

`python` / `python3` 解析到 `C:\Users\Yim\AppData\Local\Microsoft\WindowsApps\python.exe`， 那是 Windows Store 的占位符：**`python --version` 输出空字符串，脚本静默失败、无报错**。 本会话照旧记忆写了个 `python - <<'PY'` 改文件，命令"成功"返回但文件一个字没动， grep 验证才发现。

**改用 `node`（v24 可用）：** `fs.readFileSync(p, "utf8")` / `fs.writeFileSync(p, s, "utf8")` （Node 的 "utf8" 不带 BOM，正是要的）。

### node 的坑：Windows 路径反斜杠会被吞

shell 单引号里写 `node -e '...D:\\Mods\\x...'`， 经 shell 传给 node 后 `\M` 是无效转义 → 被吃成 `M`，路径变成 `D:Modsx`， `replace` 静默不命中。本会话踩了两次。 **含 Windows 路径的脚本一律用 Write 工具写成 `.js` 文件再 `node <file>` 执行**， 不要走 `node -e`。写文件后 grep 验证结果，别只看 "OK"。

### ⚠ `node - <<'EOF'` 也吞反斜杠（2026-09-12 核实）

不只是 `node -e`。Bash 工具的 quoted heredoc 把脚本喂给 `node -` 时，脚本源码里的 `\s`、`\.`、`\n` 全被吃掉一层：正则 `^(\s*)"key"` 到 node 里成了 `^(s*)"key"`， 静默不命中。**改 JSON / 需要正则或转义字符的 node 脚本，一律不写任何反斜杠**： 换行用 `String.fromCharCode(10)`，找行用 `indexOf`，不用正则； 或者按上面说的用 Write 工具落成 `.js` 再 `node <file>`。 纯字符串 `includes` / `replace(字面串)` 的脚本没问题，只要字面串里没反斜杠。

### Bash 工具的 heredoc 会被未配对单引号打断

`cat > x.py <<'EOF'` 里只要内容含未配对的 `'`（英文撇号，如 `entity's`、`task's`）， 就报 `unexpected EOF while looking for matching`。

**How to apply:** 含中文或撇号的长文本，一律用 Write 工具写成脚本文件（`.js`）再执行， 不走 heredoc、也不走 `node -e`。

例外：**纯追加**长文本到 md（写日志那种）用 `cat >> file <<'EOF'` 是稳的， 本会话用了多次没出问题 —— 前提是内容里没有未配对的英文撇号。

### 这个工作区有多个写入方

用户会同时用别的 agent / 编辑器改同一个仓库。**mtime 不能用于归因**： 本会话见过「我一次性顺序写的两个文件时间戳差 2 分钟」「没碰过的文件出现在改动窗口内」。 大动作前先按安全手册做带时间戳的备份（`D:\Mods\项目备份`）。

**Why:** 2026-09-02 出过一次编码事故，已写进协作指南「事故教训」一节。 **How to apply:** 编码类操作先小样本探测（写 1 行 → 读回验证）再整文件处理。 改完 JSON 一定用解析器验一遍：本会话就因为一个 `.replace` 多加了个逗号， 把 `zh_cn.json` 变成非法 JSON，整个中文语言包加载失败。

### TASK 必须执行方中立

用户不一定把 TASK 拍给 DeepSeek —— 可能是 mini、Codex 或别的 agent，也可能自己做。

**Why:** TASK 里写「你是 DS，要遵守协作指南第 N 节」，换个执行方就完全失效； 文件名带 DS 也会让别的 agent 困惑。 **How to apply:** TASK 只写「要做什么」加必要的背景事实，完全自包含 —— 不引用协作指南、不出现 DS 字样、不假设执行方了解项目历史。 新建 TASK 命名用 `TASK_00N_描述.md`。

### 不要追问「谁来执行」

**Why:** 每轮问「要我直接做还是写成 TASK」是纯噪音。判断任务规模是 Claude 自己的职责， 不是需要用户拍板的设计决策 —— 用户拿到产出后自己会决定拍给谁。 **How to apply:** 判断完规模直接产出。小任务（≤3 个文件、不跨模块）自己做完再汇报； 大任务直接写成 TASK 文件、给出路径。做完再说，不要先问。

### 核心原则

1. 不默认大范围探索 —— 从最小范围开始，证据不足才扩大。
2. 昂贵调查在开始前就委派，不要自己查完才写 TASK。
3. 原始日志、grep 全量结果不要污染主上下文。
4. 验收交付物时逐条 grep 核实主张，但命令要合并；不重复执行方已完成的调查。
5. 达到验收标准立即停止，不顺便优化无关内容。
6. 只做用户要求的最小修改，不做无关重构。
7. 重要 API / 函数 / 行为必须基于实际项目验证，不凭记忆假设。
8. 已读取且未变化的文件不要重复读全文。
9. 大型 / 破坏性操作前按安全手册备份。
10. 持久记忆只保存稳定、未来有用的信息。

### 任务规模阈值（参考，非硬限制）

**委派**：读取 >8 个文件、分析 >500 行日志、修改 >5 个文件、大范围调用链调查、批量机械操作。 **自己做**：1~3 个明确文件、少量代码、单函数或配置调整、明显低风险的小 Bug。
