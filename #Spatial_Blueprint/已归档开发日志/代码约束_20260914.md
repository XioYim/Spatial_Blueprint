## 这是什么

- Spatial Blueprint —— Minecraft 1.20.1 / Forge 模组，modid `spatial_blueprint`，源码 198 个 `.java`。
- 工程 Forge 版本 `forge_version=47.4.10`（`gradle.properties`）；实机测试服务端 `XioYim_Server` 为 Forge 47.4.16。
- **协议版本 = mod 版本**；当前部署 **2.6.8**（`spatial_blueprint-2.6.8.jar` = 1,068,911 字节 / SHA256 `C3B6F7B9`…，双端）。

## 构建与警告基线

- 验编译：`.\gradlew.bat compileJava --offline --rerun` → 要 `BUILD SUCCESSFUL`（增量 `classes` 会 UP-TO-DATE，一条不打印，验收一律带 `--rerun`）。
- **警告基线 21 条**（2026-09-14 实测，`BUILD SUCCESSFUL`；按 `\.java:\d+:` 计数 —— 这台机器 javac 输出中文，按 `warning` 数恒为 0）。
- 构建：`.\gradlew build --offline` → `build\libs\spatial_blueprint-<版本>.jar`；离线证书问题加 `-Dnet.minecraftforge.gradle.check.certs=false`。

## 网络协议与发版

- **发版必须 bump mod_version**：2.4.0 这个号下曾经存在两个不同产物（718KB 有 bug / 1024KB 已修），线上出问题时光看版本号根本分辨不出手上是哪份。
- **新增消息必须走 `BlueprintNetwork.c2s()` / `s2c()`，且只能追加在 `register()` 末尾。** 注册顺序就是线上的消息序号，插队 / 删除 / 改方向都必须 bump mod_version 并同时更新双端。 方向标反的后果是玩家一发那条消息就被踢下线（「Illegal packet received」），不是静默失败。
- 新增 S2C 字段：encode/decode 对称、客户端缓存整份替换、wire 变了 bump mod_version。

## 客户端 / 服务端边界

- **上传判定用服务端配置**，勿用 `S2C_ConfigSyncMessage.slotLimitFor` 客户端镜像。
- **服务端读蓝图数据一律用 `getBlueprintDataServer` / `getMaterialListServer`。** `FMLEnvironment.dist` 是物理端，单人与局域网主机上它等于 CLIENT， 拿它当逻辑端用就是 H3 那个坑。tooltip 是唯一可以按物理端分派的场景 （`getMaterialListForTooltip`），别照抄到别处。
- 客户端会话缓存新增时，**必须挂 `ClientPlayerNetworkEvent.LoggingOut` 复位**， 否则上个服的状态会带进下个服。例外只有 `ClientPreviewSettings`（本地 json 持久化设置）。
- **改完主类或任何非 client 包的类，验产物不验源码**： `javap -p -c SpatialBlueprintMod.class | grep net/minecraft/client` 必须 0 命中。 编译通过不是证据 —— 内联 lambda 会把 `Screen` 带进主类的 synthetic 方法签名， FML 在 CONSTRUCT 阶段解析描述符时就会让专服起不来，任何运行时 dist 判断都来不及。 客户端类型只能出现在 `client/`、`gui/` 包，或带 `@OnlyIn(Dist.CLIENT)` 的成员上。 （注：`javap -v` 的**类级注解在输出末尾**，别用 `head`/`tail -20` 去取，会误判。）

## 权限与归属

- **归属判断一律用 `ownerUuid`，不要用 `creatorName`** —— 后者是捕获当时的玩家名， 改名就对不上。唯一例外是无主旧数据（`ownerUuid` 为空）的**可见性**回退， 见 `BlueprintLibraryScreen.isMineForListing`；**权限判断不许放宽**，无主一律判否。
- **会写别人蓝图文件的操作一律走 `BlueprintValidator.canManageBlueprint`**（主人或 OP； 无主蓝图只有 OP 能碰）。`isCreative()` 只表示「这是蓝图库管理场景」，不等于有权动这一份， 两道都要过。次元蓝图删除另有自己那套三段式判定，别用本入口顶掉它。
- WorldOwn 归属判定禁逐条 INFO（高频）。

## 世界改动 / 捕获与净化

- **任何会改动世界方块的路径，创造模式是否受领地检查一律看 `DENY_CREATIVE_PLACEMENT_IN_PROTECTED_AREA`**（默认 true），不要硬编码 `!isCreative()`。 已接入：放置两处 + 次元捕获 + 虚空重捕获。新增这类路径时照抄这个判定。 例外是放置侧的「结构冲突预检」（挡道方块），那个跟领地无关，只看游戏模式是对的。
- 三种超限语义不同：单体体积/深度 → 清 NBT 保留方块；体积总量 → 拒收。捕获路径刻意无限制。
- **两个 strip 方法分工别搞混**：`stripDangerousBlockNbt` 无条件倒容器（上传净化、 `effectiveNbtBytes` 用它）；`stripDangerousBlockNbtKeepContents` 保留容器（次元蓝图捕获用）。 安全项两者都做，共用 `applySafetyStripInPlace`。给次元蓝图加容器清理 = 回归。
- **次元蓝图只有 SAFE 一条路，任何人一样，OP 不豁免**（2026-09-12 用户拍板）：服务端 `CaptureAreaMessage` 对 `clearAfterCapture && effMode != SAFE` 直接拒；非法方块 / 方块实体 `hasDangerousBlockNbt` / 实体 `findEntityWithIllegalItems` 三道预扫任一命中整单拒，都在清世界之前。**捕获预扫与扫描报告 `C2S_RequestIllegalBlocksMessage` 必须用同一组判定**（`entityHasIllegalItems` 等），报告标危险的服务端必拒、 报告没标的必放，否则玩家没法自己清理。给次元蓝图加任何净化 / OP 放行 = 回归。
- FORCE 模式对次元蓝图不可达：`BlueprintReportScreen` 的 OP 按钮会把 category 强制覆盖成 `create`/`reward`。别再设计依赖「次元 + FORCE」的方案。
- 深 JSON 靠体积检测封顶（`maxBlockEntityNbtBytes`），不是靠 65535 —— 两个阈值同时是两套防线， fail-closed 修法已完成（TASK-007 PASS）。`catch(Throwable)` 保持（收窄会让 OOM 冒泡到网络线程被静默吞）。

## Create 胶水与盒型实体

- **Create 胶水的 `From`/`To` 是相对 `Pos` 的偏移，不是世界坐标**（存盘 `bb.move(-pos)`， 读盘 `+pos`，`Pos` = 盒底中心）。捕获几何一律取 `entity.getBoundingBox()`；放置写回 `Pos=(cx, minY, cz)`、`From=lo−Pos`、`To=hi−Pos`。把 From/To 当世界坐标就是 2.6.0~2.6.3 那个「一个胶水都捕不到」的坑。
- **盒型实体（From/To 角点）的坐标变换走 `BlueprintTransform.cornerX/cornerZ`，公式不带 `-1`。** 方块索引跑 0..size-1，角点跑 0..size，两套公式不能混用 —— 混用的表现是整个盒子偏一格。 旋转后 From/To 会对调，**必须重新按 min/max 规范化**，否则写出反向 AABB。 新增这类实体只要往 `BOX_ENTITIES` 配置里加 ID，不要在代码里引用对方 mod 的类。

## 配置与界面

- 配置界面一律走 `ConfigAccess`（服务端镜像 + 提交），不直写本地 toml；列表/数字快照刷新按 `ClientConfigMirror.snapshotVersion`。
- BuildTime 档位仅客户端显示估算（PointSelectionScreen），服务端权威，属可接受显示不一致，暂不投影。
- **查 `ValueSpec`（范围/默认）用 `SPEC.getSpec().get(path)`，不是 `getValues()`** —— 后者那张表放的是 `ConfigValue`，`instanceof ValueSpec` 永远不中，兜底分支会静默放行。 只要默认值，直接 `value.getDefault()`，不用查表。

## 文本与提示

- **lang 占位符一律 `%s` / `%1$s`**，原版 `TranslatableContents` 不认 `{0}`，会原样画出来。
- Spatial Blueprint 的**所有报错提示一律用 ErrorToast 横幅**，不要用 `player.displayClientMessage()` / `sendSystemMessage()` 发到聊天栏。 有宿主界面时：Screen 实现 `ErrorToastSupport`，在 `render()` 开头用早返回模式渲染； **没有宿主界面时**（如在世界中右键物品触发的报错）： `Minecraft.getInstance().setScreen(new ErrorToastScreen(message))` —— `ErrorToastScreen` 是专为这种场景写的独立横幅界面，任意点击或 ESC 关闭，不暂停游戏。 服务端发 `S2C_OperationResult(false, key)` 时，客户端若有 `ErrorToastSupport` 界面会自动转成横幅；但那条路径在无界面时仍会回落到聊天栏，需要横幅就自己开 `ErrorToastScreen`。成功类通知可以走聊天栏，但注意 `S2C_OperationResult` 的成功分支会**关闭** `PointSelectionScreen` / `PlacementScreen`，不想关界面就别用它。 接入方法见 注意事项「常项参考：报错横幅（ErrorToast）接入」卡（原文已归档）。 用户 2026-08-13 明确要求以后所有报错都走横幅。 **Why:** 聊天栏提示太容易被玩家忽略，尤其在世界中操作物品时视线不在聊天区。

## 推送与 NBT 规则

- **服务端把蓝图发给客户端，只能走 `BlueprintNetwork.sendBlueprintTo`**（TASK-006，2026-09-03）。 它序列化一次、压缩一次、按 `S2C_BlueprintChunkMessage.CHUNK_SIZE` 切片，**一个 chunk 也分片，没有 size 分支**；超 `MAX_TOTAL_CHUNKS`(256) 只记 warn 不发。 `S2C_BlueprintDataMessage` **故意保留**（类 + 注册 + 范围校验都在），但它是整包发送，超过 1 MB 会在 decode 被拒。 看到 `new S2C_BlueprintDataMessage(` 出现在发送位置就是回归。 **Why:** 曾经有六处服务端主动推送直接 new 这个整包消息 —— 大蓝图捕获成功、文件已落盘，推送却被拒，玩家看到的是空预览，得重开蓝图库下载一次才有（拉取路径一直是分片的）。类没删是因为删除超出当时的任务范围，不是因为还该用。
- NBT 预算规则句：三种超限语义、两个 strip 方法分工见上面「世界改动 / 捕获与净化」；原理与理由见 注意事项「NBT 预算语义与 strip 分工（原理）」卡。
